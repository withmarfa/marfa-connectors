# GitHub

Reads the repositories a personal access token can reach or a GitHub App is installed on, their issues, issue comments and pull requests, with sub-issues, blockers, related issues, duplicates and closing links, into `github.repository`, `github.issue`, `github.comment` and `github.pull_request` rows at the feed tier, and carries changes made in Marfa to issues and comments back to GitHub, where they appear under the App's name. Personal access token runs are always read only.

## What syncs

- **Repositories**: every repository visible to the personal token, or every repository of every installation of the App, narrowed by `GITHUB_REPOSITORIES` when set, so the App can see more than is synced. A repository is a `github.repository`, read only. One synced before and left out of `GITHUB_REPOSITORIES` since is paused: nothing of it is read or written and its rows are left as they are, bar `private`, which follows its last known visibility, a change made to them in Marfa waits and is named, and a relation drawn to one of its issues is taken back and named; named again, it is taken up where it stopped. A setting changes nothing on its own, so a typo or a rename on GitHub pauses a repository rather than archiving it. An entry the selected authentication method cannot see is named in each run.
- **Issues**: everything open, and what closed or changed in the last ninety days; an older issue comes in once anything happens to it, or when an issue in the sync names it as its parent, blocker, related issue or canonical issue. Each is a `github.issue`, a core task: its title, body, labels and assignees, and its state as the task's status (`pending` while open, `completed` when closed as completed, `canceled` when closed as not planned or a duplicate, with `state_reason` saying which). Pull requests have their own type below.
- **Pull requests:** open ones and those closed or changed in the last ninety days, as read-only `github.pull_request` rows on `core.task`. Each includes its title, body, author, repository and privacy, open/closed/merged state, draft flag, merge time, base and head branches, and head-commit check rollup with nonzero counts by check-run and commit-status state. Open maps to pending, merged to completed, and closed without merging to canceled. Polling follows all pages and refreshes checks even when GitHub has not changed the pull request's `updated_at`.
- **Closing links:** `github.closes` connects a pull request to each synced issue in GitHub's `closingIssuesReferences`; body text is never parsed for links. A closed issue's latest `ClosedEvent.closer` supplies `github.closed-by` to the synced pull request that actually closed it, or `closed_by_url` for one outside the sync. Merely linking a pull request does not establish that it closed an issue. Both connections are read only.
- **Comments** on those issues, each a `github.comment`, a core message from its author, in its issue's thread through Marfa's own `in-thread`.
- **Relations**, as connections: `github.sub-issue-of` from an issue to its parent, `github.blocked-by` from an issue to each issue blocking it, `github.relates-to` between related issues, `github.duplicate-of` from a duplicate to its canonical issue, and `github.in-repository` from each issue and comment to its repository. A parent or blocker in a public repository the connector does not sync, because the App is not installed on it or `GITHUB_REPOSITORIES` leaves it out, is kept as its address, in `parent_url` or `blocked_by_urls`, until it is synced. Related issues and canonical issues outside the sync are kept in `related_urls` and `duplicate_of_url`. A relates-to pair is stored once, from the lexicographically lower GitHub node ID to the higher one, regardless of which end GitHub lists. A new relation drawn in the reverse direction is sent to GitHub and kept until the next read puts it in canonical order. A redundant reverse edge for an existing relation is removed in the same run. The App's installation tokens reach only the repositories it syncs, so GitHub shows it nothing of a private repository it does not sync, not even as the end of a relation: such a relation is not known at all, whether the App is not installed there, `GITHUB_REPOSITORIES` leaves the repository out, or it is under another installation of the App. A relation to an issue in a repository synced before and left out since stays, as that repository's rows do.

Each row links to GitHub by `github_id`, the GitHub node id of what it is.

## What travels back

With a GitHub App, every `github.issue` and `github.comment` on the instance syncs, whoever made it and under whatever source; something meant to stay in Marfa is a core task or message instead. Repositories and pull requests are read only; edits to pull request fields and closing connections are restored from GitHub. A row made in Marfa is sent as a new issue or comment; one made by hand with a `github_id` of its own is never taken for what GitHub has, so a relation or thread drawn to it waits.

Every write finds its target by the node id agreed with GitHub, asking GitHub where that issue or comment is now, never by a row's `repository` or `number`: a repository renamed or an issue transferred between repositories the App reads is followed, and an old name taken by another repository changes nothing. A target in a repository the connector does not sync or has paused is not written: the change waits and is named in the run. One the App can no longer find under any installation, while every synced repository still reads, is not sent and is settled, and the run names it: unlike a change GitHub refuses, which waits until the row changes, there is nowhere left to send it, and the daily check, or a delivery naming it, archives the row. While any synced repository is out of reach, such a change waits instead, as it does where the repository the row sits in, as agreed with GitHub, has its issues turned off, since GitHub does not say whether it still shows them. A relation is the exception: one drawn to an issue the App may not relate to, for any of those reasons, is taken back in Marfa and named, rather than waiting.

Each `github.issue`, `github.comment` and `github.pull_request` carries a read-only `private`, whether its repository is private on GitHub, as of the last scheduled run; the repository row carries the same. A change of a repository's visibility is put on every issue, comment and pull request held under it on the next scheduled run, using the repository metadata, whether or not GitHub changed the rows, and so is the first run after an upgrade that brought the field. A repository the App can no longer read has its rows marked private, since its visibility is not known. A webhook-driven run marks what it reads from the repository's visibility then. A change in `private` is not activity on an issue: it brings no trashed issue back. A row in the bin takes the value when it leaves it, by a restore or by GitHub's activity, since the instance refuses a write to a row in the bin. A comment whose issue was transferred to a repository the App does not sync keeps its original repository's value. The field is a marker and no more: the connector does not stop anyone copying a row's contents elsewhere, and Marfa gives a key access by type and connection, not by this field, so anyone able to write `github.issue` rows can still create an issue in a public repository from a private one's row. Read it before copying. Where the two types on the instance were registered before the field, the connector adds it to each on its first start, as `template/README.md` says.

- **Issues:** the title, body, labels and assignees, and the status: `completed` closes the issue as completed, `canceled` as not planned, and anything else reopens a closed one; a status GitHub has no word for, such as in progress, stays in Marfa on an open issue. An assignee GitHub will not assign is named in the run.
- **An issue made in Marfa** is created in the repository its `github.in-repository` names; without one it is not sent, and the run says why. What the App makes ends with a mark, an HTML comment GitHub's page does not show and the connector leaves out of what it reads, so where GitHub made it and answered with a server error, or the answer was lost, it is found by its mark, at the end of what the App wrote, rather than made again: at once, or, where GitHub does not list it yet or the look fails, by the next run, which looks before sending anything; meanwhile the create waits and its repository is not read, so what GitHub made never comes in as a row of its own, while the rest of the run goes on. It is brought to what the row says by then. A create is never sent twice by a retry. A row trashed before that answer came cannot take the link, so what GitHub made comes in as its own row, and the run says so.
- **Relations:** a `github.sub-issue-of`, `github.blocked-by` or `github.relates-to` drawn or removed in Marfa is made or removed on GitHub; one GitHub refuses, such as a sub-issue across two owners, is taken back in Marfa and named. Duplicates are read only: a `github.duplicate-of` drawn, removed or changed in Marfa is put back from GitHub. A repository or thread changed in Marfa is put back, since GitHub cannot move either that way.
- **Comments:** one made in Marfa in an issue's thread, through `in-thread`, is posted there, and its edits follow; its `from` becomes the App's. Only comments the App wrote take edits from Marfa: an edit to anyone else's is put back, and the run says it was not sent.
- **A trash closes, never deletes.** Trashing an open issue closes it as not planned, and one already closed stays as it is; restoring it from the bin sets its state again as its status says, so what the trash closed reopens; a reopen, an edit or a comment on GitHub while it is in the bin brings it back, as GitHub has it; a purge is remembered, and it stays closed on GitHub. A trash that came from another row's is not carried. A comment the App wrote follows the ordinary rule: a trash deletes it on GitHub, a restore makes it again, and one deleted on GitHub is archived when its delivery arrives, or at the daily check. Anyone else's comment stays on GitHub when its row is trashed, the row stays in the bin, and the run says so; one GitHub lost is not posted again under the App's name.
- **What GitHub refuses**, such as a change in an archived repository, a label too long or an issue with no title, is named in the run and stays a change in Marfa: it is not sent again as it stands, and once the row changes, all of it that differs from what GitHub holds is sent. The rest of the run goes on, and relations drawn beside it are still made. What GitHub cannot answer now, such as a server error or a spent rate limit, waits and is sent again next run.
- **Lost access** changes nothing: a change to a repository the App can no longer reach, through an uninstalled or suspended installation or a repository taken from it, or while GitHub's rate limit is spent, waits and is named in the run, and is carried once access is back.

`GITHUB_READ_ONLY=true` runs it read only as a whole: nothing goes back, a change made in Marfa to a synced field or connection is put back and named, and the setup asks GitHub only to read.

## How changes are noticed

A scheduled run lists each repository's issues whole, open and within the window, page by page, asking each page with the ETag it last answered: a page that did not change answers 304, which costs nothing against GitHub's rate limit. A new comment moves its issue's time; an edited comment, a sub-issue or a blocker does not, which is why the listing is read whole rather than since a time, and relations are read through GitHub's GraphQL API for every issue in the window, including issues on unchanged REST pages. A related link can change without changing the REST response or its ETag. Comments are read since the last run.

A condition clears only when a successful scheduled run reaches its check and finds the problem gone. Repository metadata can establish that issues are enabled while a body read is skipped; skipped access checks remain standing. Conditions can exist without saved repository progress, so unknown identities are preserved conservatively. `issue-missing:` and `issue-moved:` keys carry no repository scope and current edges cannot identify every standing key; those families remain standing even after another repository is fully read, and can retain a resolved warning indefinitely.

GitHub's documentation says an authorized request that answers 304 does not count against the primary rate limit. The ETags are kept in the connector's state, so a run asks with the ETag the last one received; the documentation does not say whether a 304 holds across installation tokens, which last an hour. In a read-only check, GitHub answered 304 to a user token that sent the ETag given to another token of the same user, so a 304 is not tied to one token, but this was not checked for installation tokens. The connector keeps its tokens between runs only under `--every`; a `--once` run mints its own. A token is minted for the repositories it reaches, so a change to which are synced or paused asks for a new one. An installation has a minimum budget of 5,000 REST requests and a separate budget of 5,000 GraphQL points per hour; GitHub can grant higher limits based on the installation. A first sync reads each repository's open and recently closed issues and all its comments, pull requests' included, a request per hundred of each: 500 issues and 2,000 comments are about 30 REST requests. GraphQL relationship and pull-request pages use the separate point budget. The daily check reads the comments whole again. Before each read request, the connector checks the installation's last reported budget for that API, REST or GraphQL, against a 500-request or 500-point reserve. A low budget or a rate limit that cannot be retried promptly leaves unfinished repositories waiting for the next run. After each repository finishes, the connector checkpoints its progress through the kit, so a later failure keeps completed work. Refused rows or an uncertain checkpoint acknowledgment leave that repository's progress unconfirmed; the next run reloads acknowledged state and replays unfinished work.

When installation enumeration waits, previously acknowledged issues, including archived issues identified by their kit agreements, remain available as relationship targets without their repositories being read. A parent or blocker never imported from a waiting repository stays as its GitHub URL. A delivery run still applies named changes from healthy installations. If the installation inventory is incomplete and any named issue or comment remains unobserved or unapplied, the run fails and retains its deliveries for replay; it does not infer deletion from an incomplete check. Already applied changes are replayed without rewriting unchanged rows.

Pull request, check-run and check-suite deliveries read the pull requests they name. Commit-status deliveries resolve the commit's associated pull requests; a commit with no pull request changes nothing. These reads leave the scheduled listing cursors unchanged. Repositories with issues disabled still sync pull requests.

With the App's webhook pointed at the instance, run the connector as `--every 1h --look-every 10s`: GitHub's deliveries for issues, comments, sub-issues, blockers and related issues each name what changed, and within seconds a run lists the App's installations and each one's repositories, then asks GitHub for those issues and comments by node id, with the issues at the other end of their relations, and reads no repository's listings, leaving their cursors for the next scheduled run. A delivery naming an issue or comment GitHub no longer has, in a repository the App still reads, has it asked after as the daily check asks. A change to an installation or a repository has the next run read everything. Deliveries are checked against `GITHUB_WEBHOOK_SECRET`, and one that fails is rejected and counted in the run's report. GitHub does not send a delivery again on its own, so the hourly run still reads every listing.

Once a day, a scheduled run also asks GitHub about each row it no longer lists. Only GitHub saying so archives anything:

- An issue GitHub says was deleted (410) is archived; one it says moved to another repository (301) is archived, and the run says so, since it arrives there as a new row.
- A comment gone from a repository GitHub still reads is archived.
- A repository taken out of the App's installation has its rows archived; they come back if it is added again.
- An App uninstalled, or its installation suspended or refusing it, a repository that stops answering, or one whose issues are turned off, changes nothing: the run says so, and the rows stay as they are.
- The daily check also writes any comment a run missed.

## Setting it up

### Personal access token

Create a fine-grained personal access token for the repositories to sync, with Issues, Pull requests, Checks, and Commit statuses read access and the automatically included Metadata read access. Set it as `GITHUB_PERSONAL_TOKEN` in the secret store and leave `GITHUB_APP_ID`, `GITHUB_PRIVATE_KEY`, and `GITHUB_WEBHOOK_SECRET` unset. The connector refuses mixed authentication settings.

Set `MARFA_API_URL` and `MARFA_API_KEY` as for the App, then run `node dist/main.js --once` or `node dist/main.js --every 1h`. No App, installation, webhook, or `--setup` is needed. A token `--setup <file>` invocation returns no new secrets, writes an empty JSON object to the requested file, and creates no webhook endpoint; the empty file may be deleted. Repository discovery uses GitHub's [authenticated repository listing](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user), including repositories owned by the user, collaborator access, and organization membership. `GITHUB_REPOSITORIES` narrows that list.

Personal token runs are always read only, even if the token has write permissions. Edits to imported rows are restored from the agreed GitHub values. Creating or restoring a row never creates anything on GitHub. Changes arrive on the schedule. A rejected token fails the run and keeps existing rows and saved progress. A missing repository permission names the permission GitHub reports and leaves that repository's progress unchanged, while other repositories can finish; if every selected repository refuses permission, the run fails.

GitHub cannot narrow a personal token for one request as it can an installation token. Choose the token's repository access carefully: the read planner imports only the configured repositories, but relation reads can reveal addresses of other repositories the token can reach.

### GitHub App

A GitHub App, registered from the manifest the connector serves:

1. Mint the connector's key, as `template/README.md` says, with `--type-permission` for the six types (`github.repository`, `github.issue`, `github.comment`, `github.pull_request`, `github.file`, and `github.file.image`), `--edge-permission` for `github.in-repository`, `github.sub-issue-of`, `github.blocked-by`, `github.relates-to`, `github.duplicate-of`, `github.closes`, `github.closed-by`, `in-thread`, and `attached-to`, `--metadata-permission types=write --metadata-permission edge_types=write`, and no `--permission`: `types=write` registers the types and keeps them current, and `edge_types=write` is needed to register connection types on first start and again when an upgrade widens their endpoint constraints. After registration or widening, the kit says how to narrow the key.
2. With `MARFA_API_URL`, `MARFA_API_KEY` and, where the instance has one, its public address as `GITHUB_PUBLIC_URL`, run `node dist/main.js --setup <file>`, naming a file outside the checkout and every other git working tree, such as one in the home directory: setup refuses a file in a folder that holds a `.git` or under one. Open the address it logs, continue to GitHub, create the App, named Marfa Connectors unless `GITHUB_APP_NAME` names another (GitHub holds each name once, so a second person's App needs its own), and install it on the repositories to sync from the address the setup logs next. For an organization's App, set `GITHUB_ORGANIZATION`.
3. Move the three secrets the file holds into the secret store and delete the file.

Without a public address the App's webhook is off, and the connector notices changes by polling alone. Run the setup again with `GITHUB_PUBLIC_URL` and the App's two secrets in the environment to point the App's webhook at the instance with a new secret, as when the instance moves. Each setup makes a new webhook endpoint, labeled with when it was set up, and names its id; retire the one it replaced with `marfa connectors endpoints retire <connector-id> <endpoint-id>`. A setup that fails retires the endpoint it made, or names it with the command to retire it by hand where the instance would not.

## Environment

- `GITHUB_PERSONAL_TOKEN`: a fine-grained personal access token, a secret. Use it alone, without the three App settings. Runs are always read only.
- `GITHUB_APP_ID`: the App's id, required only for App runs.
- `GITHUB_PRIVATE_KEY`: the App's private key, a secret. Installation tokens are made from it for an hour at a time, each reaching only what it is for, as below, and kept out of every log.
- `GITHUB_WEBHOOK_SECRET`: the secret GitHub signs deliveries with, a secret.
- `GITHUB_READ_ONLY`: `true` for every kind, or a comma-separated list of `repository`, `issue`, `comment`, `pull_request`, `file`, and `image`. With an App, a listed kind is read only and its imported rows' local edits are put back; other kinds can still carry changes. The `issue` setting also covers writable issue relations, including related issues; comments remain writable unless `comment` is listed too. Duplicate connections are always read only. Repositories, pull requests and retained files are always read only. `false` or unset keeps App issues and comments two-way. Unknown kinds and empty list members refuse startup. Personal token runs stay read only with any valid setting.
- `GITHUB_REPOSITORIES`: the repositories to sync, as `owner/repo` or `owner/*`, set apart by commas or spaces, in any case; optional, every repository the selected authentication method sees otherwise. A malformed entry stops the start.
- `GITHUB_PUBLIC_URL`, `GITHUB_ORGANIZATION`, `GITHUB_APP_NAME`: for the setup, optional. The public address's own path, where the instance sits behind a prefix, is kept before the webhook's.
- `GITHUB_API_URL`: optional, for a stub of the API; GitHub's otherwise. GitHub Enterprise Server is not tested.

The key and the run are as `template/README.md` says.

## Its tokens

Each installation token the connector asks GitHub for reaches no more than its use needs, naming repositories by GitHub's id, so a rename changes nothing:

- One lists which repositories an installation holds, and reads nothing else.
- One reads the issues, comments, pull requests and checks of the repositories synced, and of those paused, so their relations stay.
- One finds where an issue or comment named by a change sits, reading only, across the repositories the connector holds under the installation. Where GitHub will not name one of them, as for a repository taken from the installation since the last scheduled run, or one whose id is not yet recorded, it reaches the whole installation instead; a change is still carried only into a synced repository.
- One for each change made in Marfa writes issues and comments only in the synced repositories that change touches: its own, and that of the issue at the other end of a relation it draws or removes. A paused repository is never among them. Where GitHub will not mint one, as for a repository gone from the installation since the last scheduled run, only the changes touching that repository wait. A change in a repository whose id is not yet recorded waits for the next scheduled run, which records it, and the run says so. With `GITHUB_READ_ONLY=true`, or both `issue` and `comment` listed, no write token is requested.

GitHub names at most 500 repositories to a token, so past that many synced or paused under one installation, the token that reads reaches every repository of it, and the run says so; a token for a change names far fewer.

An installation token GitHub refuses after it was kept, as when it is revoked, is replaced and the request sent once more. A personal token is never replaced automatically: a 401 fails the run and names `GITHUB_PERSONAL_TOKEN`. Its REST and GraphQL budgets are tracked separately under a hash of the token, without retaining the token in a budget key.

A clock out of step with GitHub's by up to ten minutes is allowed for: what GitHub's answer says of its time is used to sign the App's requests from then on. Past ten minutes the connector asks GitHub nothing, and each run says so until the clock is set right; a change made in Marfa meanwhile waits.

## Retained attachments

Images signed in GitHub's rendered issue and comment HTML are retained as `github.file.image` on `core.file.image`. Other signed assets use `github.file` on `core.file`. Each asset uses its immutable UUID and connects to its issue or comment through `attached-to`. An asset repeated in several bodies keeps all known parents. Parent and repository node IDs determine provenance; repository names are descriptive. Its `private` marker remains true while any known parent is private or its repository has unknown visibility, including after access is removed and a retained file is restored.

Downloads use HTTPS with no GitHub authorization, cookies, or referrer. Only `private-user-images.githubusercontent.com`, `objects.githubusercontent.com`, and the narrowly matched `github-production-user-asset-*.s3.amazonaws.com` hosts are allowed, including at every redirect. Downloads are limited to 25 MiB, four redirects, and 30 seconds; both declared and streamed lengths are checked. Signed addresses stay in memory and are never written into item properties or saved progress.

A failed or expired address is retried from fresh rendered HTML on a later run, even when the issue listing has not changed. The last good file is kept. A retained UUID reuses its blob receipt, so a changed signature or parent text does not redownload or upload the same bytes. Removing a link from GitHub does not delete retained bytes, and a file removed in Marfa is not recreated.

GitHub does not provide signed download addresses for some uploaded files. Their links stay in the original body. The issue or comment's read-only `github_files` object contains `repository_id` (immutable repository node ID), `body` (SHA-256 of the imported Markdown), `assets` (retained UUIDs), `pending`, and `not_kept` (stable addresses with safe reasons). File provenance in `github_parents` maps parent node IDs to `type`, `repository_id`, `repository` (descriptive name), and `private`. Unavailable asset UUIDs each remain pending for fresh HTML even when another asset in the same body succeeds. Unsigned upload URLs are accounted for in rendered links and visible text, including Markdown left as text after an HTML block. Attachment examples inside rendered code blocks are ignored. No placeholder file row is created without bytes. The connector does not use a signed-in browser or forward API credentials to download these links. Pull request bodies and Discussions are outside this attachment import.
