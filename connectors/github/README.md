# GitHub

Reads the repositories a personal access token can reach or a GitHub App is installed on, their issues, discussions, comments and pull requests, with sub-issues, blockers, related issues, duplicates and closing links, into `github.repository`, `github.issue`, `github.discussion`, `github.comment` and `github.pull_request` rows at the feed tier (with a personal token, also the repositories its owner has starred, as `github.repository` rows), and, with a second token, the person's notifications into `github.notification` rows, and carries changes made in Marfa to issues, discussions and comments back to GitHub, where they appear under the App's name. Personal access token runs are always read only.

## What syncs

- **Repositories**: every repository visible to the personal token, or every repository of every installation of the App, narrowed by `GITHUB_REPOSITORIES` when set, so the App can see more than is synced. A repository is a `github.repository`, read only. One synced before and left out of `GITHUB_REPOSITORIES` since is paused: none of its issues, discussions or pull requests is read, and its rows are left as they are, bar `private`, which follows its last known visibility, and the star marks on its repository row, which follow the star listing; a change made to them in Marfa waits and is named, and a relation drawn to one of its issues is taken back and named; named again, it is taken up where it stopped. A setting changes nothing on its own, so a typo or a rename on GitHub pauses a repository rather than archiving it. An entry the selected authentication method cannot see is named in each run.
- **Starred repositories:** with a personal token or, failing that, the notifications token, every repository its owner has starred, each also a `github.repository`, read only, with `starred` (`true` or `false`), `starred_at`, the time the star was made, and `synced`, which says whether a process of the connector syncs the repository (`true`) or keeps it for its star alone (`false`). A repository both starred and in the sync is one row, marked. One that is only starred is a repository row and nothing more: its issues, discussions and pull requests are not read, and `GITHUB_REPOSITORIES` does not narrow stars, since a star is a fact about the person and not about a repository to sync. Stars are read on scheduled runs only, at most 100 to a request, and GitHub drops the entries the token cannot see after it cuts each page, so a page can hold fewer; a person with 300 stars costs at least 3 requests. A run with a token that does not list the stars keeps every mark as it was.
  - **Which token:** `GITHUB_PERSONAL_TOKEN` when it is set, otherwise `GITHUB_NOTIFICATIONS_TOKEN`; the two are never combined. The fallback lets the App, which has no user and so no stars, run beside stars. The notifications token is a classic token with the `notifications` scope and no `repo` scope. GitHub's reference says the starred listing needs no permission "if only public resources are requested", so the connector takes such a token to list public stars only. This has not been tried against a private star. Where that holds, a private repository is never in its listing, starred or not.
  - **Losing a star:** GitHub pages the listing by offset, so a star removed while the listing is read shifts the rest and one still there can be missed for that run. A repository therefore loses its mark, or its row, only when two scheduled runs in a row, both with the same token, list the stars completely and both lack it; the repositories the last complete listing lacked, and the setting of the token that made it, are kept in the connector's saved state. A listing made with the other token does not count as the first miss, so a change of token starts the count again. A star missed once changes nothing, and a listing that lists it again forgets the miss. A scheduled run that does not list the stars, because `GITHUB_STARS` is `false` or the listing failed, also forgets every miss, so the two listings are always consecutive.
  - **Unstarring:** a repository that is also synced has `starred` set to `false` and keeps its rows. Only a row whose `synced` is `false` is archived, so a repository another process syncs is unmarked and never archived, and so is a row no run has set `synced` on yet, such as one written before the field existed. The row is read again just before it is archived, so one another process took up meanwhile is unmarked instead. A star-only row is archived only when the run listed every repository it reads as well, since a listing that did not answer may be why a repository is missing, and starring it again brings the same row back. A repository that leaves the sync but is still starred keeps its row, which then reads `synced` as `false`, and loses the rest. A paused repository, left out by `GITHUB_REPOSITORIES`, keeps its row, and its star mark follows the listing like any other.
  - **An owner that refuses the token:** GitHub leaves a star out of the listing, without saying so, when the repository's owner refuses the token, such as an organization that limits fine-grained tokens by lifetime. So before it archives a star-only row, the connector reads the repository with the same token that listed the stars. With `GITHUB_PERSONAL_TOKEN`, a 404 or a 200 archives it: the repository is gone, the token can see it and it is not starred, or, for a private repository, the token has lost access to it, which GitHub also answers 404. The row comes back when a listing shows it again. With `GITHUB_NOTIFICATIONS_TOKEN`, only a 200 archives it, since the token sees public repositories only and answers a private one 404 as it does a deleted one. With the personal token, then, a 404 still archives a star-only row, including a private one the token lost access to; archiving is reversible, since the same row returns when a listing shows the star again. Any other answer, including a spent rate limit, keeps the row and names `stars-kept`, which lists the repositories and the answer GitHub gave, in the run whose listing confirms the miss. The row stays marked and is read again on each run, and the condition clears on a scheduled run that lists the stars and finds nothing left to keep.
  - **When stars cannot be listed:** because of a failed page, a spent rate limit or a token without Starring read access, the run changes no mark, archives nothing for a lost star, forgets the misses it held, so the count starts again, and names `stars-unreadable`, which clears when a scheduled run lists them.
  - **Private stars with the notifications token:** a missing star proves nothing about a private repository, so a synced private repository marked starred keeps its mark, and a private repository that is only starred keeps its row, marked, however many listings lack it, and the connector makes no read of it, since this token can only be answered 404. Both are named in `stars-kept`, from the first listing that lacks them, and a miss under this token is not kept for a later run with another token. Such marks come only from an earlier run with a token that sees private repositories, such as `GITHUB_PERSONAL_TOKEN`. A private repository that was never marked reads `starred` as `false` even when it is starred, since this token cannot see the star.
  - **Without a token:** with the App and no notifications token, no stars are read, the run does not read the repository rows to carry marks, and the `starred` fields are empty. With the App and the notifications token, every delivery, scheduled or not, still reads the repository rows to carry the marks.
  - **Registered types:** a key without `types=write` cannot add the three fields to an already registered `github.repository`, so the run goes on without them and names the command that adds the permission. Without `synced`, no row says it is star-only, so a lost star only unmarks a row and never archives it.
- **Issues**: everything open, and what closed or changed in the last ninety days; an older issue comes in once anything happens to it, or when an issue in the sync names it as its parent, blocker, related issue or canonical issue. Each is a `github.issue`, a core task: its title, body, labels and assignees, and its state as the task's status (`pending` while open, `completed` when closed as completed, `canceled` when closed as not planned or a duplicate, with `state_reason` saying which). Pull requests have their own type below.
- **Pull requests:** open ones and those closed or changed in the last ninety days, as read-only `github.pull_request` rows on `core.task`. Each includes its title, body, author, repository and privacy, open/closed/merged state, draft flag, merge time, base and head branches, and head-commit check rollup with nonzero counts by check-run and commit-status state. Where GitHub refuses a token the checks, the pull requests read through that token keep the summary read last, and one read for the first time has none; another installation of the App still reads its own checks. Open maps to pending, merged to completed, and closed without merging to canceled. Polling follows all pages and refreshes checks even when GitHub has not changed the pull request's `updated_at`.
- **Closing links:** `github.closes` connects a pull request to each synced issue in GitHub's `closingIssuesReferences`; body text is never parsed for links. A closed issue's latest `ClosedEvent.closer` supplies `github.closed-by` to the synced pull request that actually closed it, or `closed_by_url` for one outside the sync. Merely linking a pull request does not establish that it closed an issue. Both connections are read only.
- **Discussions:** every discussion of a repository that has Discussions turned on, each a `github.discussion`, a core note: its title, body, number, repository, author, category name, whether it is open or closed (`status`, with `state_reason` as `resolved`, `outdated`, `duplicate` or `reopened`), whether it is answered and whether it is locked, with `github.in-repository` to its repository. A repository with Discussions turned off is passed over without a report. A scheduled run reads each repository's discussions newest change first, down to the time the last run reached less five minutes, and follows every page of each discussion's comments and of each comment's replies. The first comments of a discussion, and the first replies to each, come with the listing itself, so a discussion with few comments costs no further request.
- **Comments** on those issues and discussions, each a `github.comment`, a core message from its author, in its issue's or discussion's thread through Marfa's own `in-thread`. A reply on a discussion is also joined to the comment it answers through Marfa's own `parent-of`, written from that comment to the reply, which the connector declares from the reply's side as `child-of`. Marfa joins replies to messages the same way. A comment deleted on GitHub that has replies stays there as a blank comment, so its row keeps its place in the thread with an empty body, and `ghost` as its author where GitHub no longer names one. One deleted outright is archived.
- **Relations**, as connections: `github.sub-issue-of` from an issue to its parent, `github.blocked-by` from an issue to each issue blocking it, `github.relates-to` between related issues, `github.duplicate-of` from a duplicate to its canonical issue, and `github.in-repository` from each issue, discussion, comment and pull request to its repository. A parent or blocker in a public repository the connector does not sync, because the App is not installed on it or `GITHUB_REPOSITORIES` leaves it out, is kept as its address, in `parent_url` or `blocked_by_urls`, until it is synced. Related issues and canonical issues outside the sync are kept in `related_urls` and `duplicate_of_url`. A relates-to pair is stored once, from the lexicographically lower GitHub node ID to the higher one, regardless of which end GitHub lists. A new relation drawn in the reverse direction is sent to GitHub and kept until the next read puts it in canonical order. A redundant reverse edge for an existing relation is removed in the same run. The App's installation tokens reach only the repositories it syncs, so GitHub shows it nothing of a private repository it does not sync, not even as the end of a relation: such a relation is not known at all, whether the App is not installed there, `GITHUB_REPOSITORIES` leaves the repository out, or it is under another installation of the App. A relation to an issue in a repository synced before and left out since stays, as that repository's rows do.
- **Notifications:** with `GITHUB_NOTIFICATIONS_TOKEN` set, every thread in the token owner's notifications, read and unread, as a read-only `github.notification` on `core.message`. Its `body` is the title of what the thread concerns and its `from` is the repository's full name. It also holds `reason` (why GitHub notified the person, which changes when a later notification on the thread has another reason), `unread`, `github_updated_at`, `last_read_at` (empty until the person has read it), `subject_type` (such as `Issue`, `PullRequest`, `Discussion`, `Commit` or `Release`), `url` (the address on GitHub of the issue, pull request, discussion or commit it concerns; empty for a subject with no page to name) and `private` (whether the repository is private on GitHub, as of the last read). Marfa's own `references` connects it to the synced `github.issue`, `github.pull_request` or `github.discussion` it concerns; a thread about anything else, or about a repository that is not synced, is a row with no connection. The connector reconciles only the `references` it wrote, so a link a person draws from a notification to anything is left as it is. The connector never marks a thread read or done and never changes a subscription. See "Notifications" below.

Each row links to GitHub by `github_id`, the GitHub node id of what it is; for a notification it is the thread's id.

## What travels back

With a GitHub App, every `github.issue`, `github.discussion` and `github.comment` on the instance syncs, whoever made it and under whatever source; something meant to stay in Marfa is a core task, note or message instead. Repositories and pull requests are read only; edits to pull request fields and closing connections are restored from GitHub. A row made in Marfa is sent as a new issue, discussion or comment; one made by hand with a `github_id` of its own is never taken for what GitHub has, so a relation or thread drawn to it waits. A conflicted copy, the row Marfa writes to keep the losing side of two colliding edits (tagged `conflicted-copy`), is not sent: it stays in Marfa, and the run raises a condition that names it.

Every write finds its target by the node id agreed with GitHub, asking GitHub where that issue, discussion or comment is now, never by a row's `repository` or `number`: a repository renamed or an issue transferred between repositories the App reads is followed, and an old name taken by another repository changes nothing. A transferred issue has a new node id, and the read gives its row that id before any change in Marfa is carried (see Transferred issues), so a change made in Marfa goes to the issue in its new repository. A target in a repository the connector does not sync or has paused is not written: the change waits and is named in the run. One the App can no longer find under any installation, while every synced repository still reads, is not sent and is settled, and the run names it: unlike a change GitHub refuses, which waits until the row changes, there is nowhere left to send it, and the daily check, or a delivery naming it, archives the row. While any synced repository is out of reach, such a change waits instead, as it does where the repository the row sits in, as agreed with GitHub, has its issues turned off, or its Discussions for a discussion or one of its comments, since GitHub does not say whether it still shows them. A new comment has no agreed placement yet, so the repository of the issue or discussion it goes into stands for it. A token for Discussions that GitHub will not mint also makes the change wait, as it does not prove the target gone. A relation is the exception: one drawn to an issue the App may not relate to, for any of those reasons, is taken back in Marfa and named, rather than waiting.

Each `github.issue`, `github.discussion`, `github.comment` and `github.pull_request` carries a read-only `private`, whether its repository is private on GitHub, as of the last scheduled run; the repository row carries the same. A change of a repository's visibility is put on every issue, discussion, comment and pull request held under it on the next scheduled run, using the repository metadata, whether or not GitHub changed the rows, and so is the first run after an upgrade that brought the field. A repository the App can no longer read has its rows marked private, since its visibility is not known. A webhook-driven run marks what it reads from the repository's visibility then. A change in `private` is not activity on an issue: it brings no trashed issue back. A row in the bin takes the value when it leaves it, by a restore or by GitHub's activity, since the instance refuses a write to a row in the bin. A comment whose issue was transferred to a repository the App does not sync keeps its original repository's value. The field is a marker and no more: the connector does not stop anyone copying a row's contents elsewhere, and Marfa gives a key access by type and connection, not by this field, so anyone able to write `github.issue` rows can still create an issue in a public repository from a private one's row. Read it before copying. Where a type on the instance was registered before the field, the connector adds it on its first start, as `template/README.md` says.

- **Issues:** the title, body, labels and assignees, and the status: `completed` closes the issue as completed, `canceled` as not planned, and anything else reopens a closed one; a status GitHub has no word for, such as in progress, stays in Marfa on an open issue. An assignee GitHub will not assign is named in the run.
- **An issue made in Marfa** is created in the repository its `github.in-repository` names; without one it is not sent, and the run says why. What the App makes ends with a mark, an HTML comment GitHub's page does not show and the connector leaves out of what it reads, so where GitHub made it and answered with a server error, or the answer was lost, it is found by its mark, at the end of what the App wrote, rather than made again: at once, or, where GitHub does not list it yet or the look fails, by the next run, which looks before sending anything; meanwhile the create waits and its repository is not read, so what GitHub made never comes in as a row of its own, while the rest of the run goes on. It is brought to what the row says by then. A create is never sent twice by a retry. A row trashed before that answer came cannot take the link, so what GitHub made comes in as its own row, and the run says so.
- **Relations:** a `github.sub-issue-of`, `github.blocked-by` or `github.relates-to` drawn or removed in Marfa is made or removed on GitHub; one GitHub refuses, such as a sub-issue across two owners, is taken back in Marfa and named. Duplicates are read only: a `github.duplicate-of` drawn, removed or changed in Marfa is put back from GitHub. A repository or thread changed in Marfa is put back, since GitHub cannot move either that way.
- **Comments:** one made in Marfa in an issue's thread, through `in-thread`, is posted there, and its edits follow; its `from` becomes the App's. Only comments the App wrote take edits from Marfa: an edit to anyone else's is put back, and the run says it was not sent. The connector still reads the comment's author from GitHub before it sends an edit or a delete, as for an issue comment.
- **Discussions:** the title and body, and whether it is closed: `status` set to `closed` closes the discussion with the reason `state_reason` names (`resolved`, `outdated` or `duplicate`, and `resolved` where none is named), and `open` reopens a closed one. The category, whether it is answered and whether it is locked are read only, and a change to one in Marfa is put back from GitHub.
- **A discussion made in Marfa** is created in the repository its `github.in-repository` names, in the category its `category` field names, found among the repository's categories by name, case apart. Without a repository, without a category, or with a category the repository does not have, it is not sent; the run names the categories the repository does have, and the change waits until the row changes. It is made once, by the same mark an issue has, so a lost answer never makes a second discussion.
- **Discussion comments:** one made in Marfa in a discussion's thread is posted there, as a reply to the comment a `parent-of` connection from that comment names, and its edits and its trash follow as for an issue comment. Trashing one that has replies blanks it on GitHub, which keeps the replies, rather than deleting it. **Trashing a comment in Marfa also puts its replies in the bin**, since `parent-of` cascades: they leave the thread in Marfa, whoever wrote them. The connector carries only the trash of the comment itself, never the trash of a reply the bin took with it, so a comment the App wrote that is trashed with its parent is not deleted on GitHub, and nothing is sent for anyone else's. A reply trashed on its own is carried as any comment's trash is, and so is a purge. Restoring the parent brings its replies back and carries only the parent's restore. On GitHub the replies stay under the blanked comment, so they need nothing sent for them. A comment someone else wrote is not edited or deleted from Marfa.
- **A trash closes, never deletes.** Trashing an open issue closes it as not planned, and one already closed stays as it is; restoring it from the bin sets its state again as its status says, so what the trash closed reopens; a reopen, an edit or a comment on GitHub while it is in the bin brings it back, as GitHub has it; a purge is remembered, and it stays closed on GitHub. A discussion has no bin on GitHub, so trashing one sends nothing and it stays as it is there. A trash that came from another row's is not carried. A comment the App wrote follows the ordinary rule: a trash deletes it on GitHub, a restore makes it again, and one deleted on GitHub is archived when its delivery arrives, or at the daily check. Anyone else's comment stays on GitHub when its row is trashed, the row stays in the bin, and the run says so; one GitHub lost is not posted again under the App's name.
- **What GitHub refuses**, such as a change in an archived repository, a label too long or an issue with no title, is named in the run and stays a change in Marfa: it is not sent again as it stands, and once the row changes, all of it that differs from what GitHub holds is sent. The rest of the run goes on, and relations drawn beside it are still made. What GitHub cannot answer now, such as a server error or a spent rate limit, waits and is sent again next run.
- **Lost access** changes nothing: a change to a repository the App can no longer reach, through an uninstalled or suspended installation or a repository taken from it, or while GitHub's rate limit is spent, waits and is named in the run, and is carried once access is back.

A `github.notification` is always read only: an edit made in Marfa to one is put back from GitHub, and nothing is ever sent to GitHub for it.

`GITHUB_READ_ONLY=true` runs it read only as a whole: nothing goes back, a change made in Marfa to a synced field or connection is put back and named, and the setup asks GitHub only to read. The kinds are read only one by one as well: `discussion` makes discussions read only and `comment` makes both issue comments and discussion comments read only. Because a comment on a discussion is written with the Discussions permission, the setup asks for that permission read only only when both `discussion` and `comment` are read only.

## How changes are noticed

A scheduled run lists each repository's issues whole, open and within the window, page by page, asking each page with the ETag it last answered: a page that did not change answers 304, which costs nothing against GitHub's rate limit. A new comment moves its issue's time; an edited comment, a sub-issue or a blocker does not, which is why the listing is read whole rather than since a time, and relations are read through GitHub's GraphQL API for every issue in the window, including issues on unchanged REST pages. A related link can change without changing the REST response or its ETag. Comments are read since the last run.

Discussions are read from the newest change down, to the time the last run reached less five minutes, so an unchanged repository costs one request. A new comment, a reply or a deletion moves the discussion's own time, but an edit to a comment does not (as of 23 October 2026), so a scheduled run does not see an edited discussion comment. Without its webhook, the edit arrives only at the daily check, which reads every discussion in full. A run also reads a discussion's comments whenever a delivery names the discussion. A repository's Discussions that GitHub refuses, because the App has not accepted the Discussions permission or the personal token lacks it, are left as they are and named in the run as `discussions-unreadable`; the other kinds keep syncing, and the condition clears when a scheduled run reads the repository's discussions.

A condition clears only when a successful scheduled run reaches its check and finds the problem gone. Repository metadata can establish that issues are enabled while a body read is skipped; skipped access checks remain standing. Conditions can exist without saved repository progress, so unknown identities are preserved conservatively. The `issue-missing:`, `issue-moved:` and `duplicate:` conditions are keyed by an issue or a row, not a repository. When a scheduled run checks a repository in full, it clears those for the repository's rows that it does not raise again, for example when the old address answers again. It keeps one for a row it did not check, such as a closed issue quiet since before the window, and one for an issue or row it never held.

GitHub's documentation says an authorized request that answers 304 does not count against the primary rate limit. The ETags are kept in the connector's state, so a run asks with the ETag the last one received; the documentation does not say whether a 304 holds across installation tokens, which last an hour. In a read-only check, GitHub answered 304 to a user token that sent the ETag given to another token of the same user, so a 304 is not tied to one token, but this was not checked for installation tokens. The connector keeps its tokens between runs only under `--every`; a `--once` run mints its own. A token is minted for the repositories it reaches, so a change to which are synced or paused asks for a new one. An installation has a minimum budget of 5,000 REST requests and a separate budget of 5,000 GraphQL points per hour; GitHub can grant higher limits based on the installation. A first sync reads each repository's open and recently closed issues and all its comments, pull requests' included, a request per hundred of each: 500 issues and 2,000 comments are about 30 REST requests. GraphQL relationship and pull-request pages use the separate point budget. The daily check reads the comments whole again. Before each read request, the connector checks the installation's last reported budget for that API, REST or GraphQL, against a 500-request or 500-point reserve. A low budget or a rate limit that cannot be retried promptly leaves unfinished repositories waiting for the next run. After each repository finishes, the connector checkpoints its progress through the kit, so a later failure keeps completed work. Refused rows or an uncertain checkpoint acknowledgment leave that repository's progress unconfirmed; the next run reloads acknowledged state and replays unfinished work.

When installation enumeration waits, previously acknowledged issues, including archived issues identified by their kit agreements, remain available as relationship targets without their repositories being read. A parent or blocker never imported from a waiting repository stays as its GitHub URL. A delivery run still applies named changes from healthy installations. If the installation inventory is incomplete and any named issue or comment remains unobserved or unapplied, the run fails and retains its deliveries for replay; it does not infer deletion from an incomplete check. Already applied changes are replayed without rewriting unchanged rows.

Pull request, check-run and check-suite deliveries read the pull requests they name. Commit-status deliveries resolve the commit's associated pull requests; a commit with no pull request changes nothing. These reads leave the scheduled listing cursors unchanged. Repositories with issues disabled still sync pull requests.

With the App's webhook pointed at the instance, run the connector as `--every 1h --look-every 10s`: GitHub's deliveries for issues, comments, discussions, discussion comments, sub-issues, blockers and related issues each name what changed, and within seconds a run lists the App's installations and each one's repositories, then asks GitHub for those issues, comments and discussions by node id, with the issues at the other end of their relations, and reads no repository's listings, leaving their cursors for the next scheduled run. A delivery naming an issue or comment GitHub no longer has, in a repository the App still reads, has it asked after as the daily check asks. A discussion comment's delivery names the comment as well as its discussion, so a comment deleted on GitHub is archived when its delivery arrives; only the comments a delivery names are archived. A discussion comment a delivery names is read through its discussion. Where GitHub refuses that read, the comment is left as it is and never archived. A change to an installation or a repository has the next run read everything. Deliveries are checked against `GITHUB_WEBHOOK_SECRET`, and one that fails is rejected and counted in the run's report. GitHub does not send a delivery again on its own, so the hourly run still reads every listing.

Once a day, a scheduled run also asks GitHub about each row it no longer lists. Only GitHub saying so archives anything:

- An issue GitHub says was deleted (410) is archived. One it says moved to another repository (301) stays the same row where the connector syncs and reads the repository it moved to (see Transferred issues); otherwise it is archived, and the run says so.
- A comment gone from a repository GitHub still reads is archived.
- A discussion GitHub no longer returns, and a discussion comment gone from one it still returns, are archived once GitHub has confirmed by node id that it is gone. A repository whose Discussions are turned off or refused changes nothing, and neither does a lookup GitHub refuses. A delivery archives a gone discussion only when Marfa holds no comment under it; one with comments waits for the daily check, which archives the comments with it. A delivery archives nothing, a discussion or a comment, while its repository's Discussions are turned off: it waits for the daily check.
- A repository taken out of the App's installation has its rows archived; they come back if it is added again. One that is still starred keeps its repository row, marked starred.
- An App uninstalled, or its installation suspended or refusing it, a repository that stops answering, or one whose issues are turned off, changes nothing: the run says so, and the rows stay as they are.
- The daily check also writes any comment a run missed, on a discussion as on an issue.

## Notifications

GitHub shows a person's notifications only to a classic personal access token (or an OAuth token) with the `notifications` scope. A GitHub App's token and a fine-grained personal token cannot read them: GitHub answers 403. The connector therefore reads them with its own setting, `GITHUB_NOTIFICATIONS_TOKEN`, beside either the App or `GITHUB_PERSONAL_TOKEN`. Create a classic token with only the `notifications` scope. GitHub also accepts the `repo` scope for this, but the connector needs nothing past `notifications`, and a token that holds only that cannot read a repository's contents. The token belongs to one person, so the rows are that person's notifications, whatever the App or the personal token reads. With no `GITHUB_PERSONAL_TOKEN`, the same token also lists the person's stars; it sees public repositories only, which Starred repositories under What syncs describes.

- **Unset:** nothing is read and nothing is reported. Rows already read stay as they are.
- **Refused:** a token GitHub rejects (401), or one that cannot read notifications (403 or 404), raises the `notifications-refused` condition, which names the setting, the scope needed and, when GitHub says them, the scopes the token holds. The other kinds carry on, and the rows already read are kept.
- **Rate limited, or any other failure of GitHub's listing:** the `notifications-rate-limit` and `notifications-failed` conditions say so, change nothing, and clear on the next scheduled run that reads them. A failure of Marfa while the rows are written is not one of these: it is reported as Marfa's, like any other. Notifications have a rate limit budget apart from the App's.
- **Narrowing:** when `GITHUB_REPOSITORIES` is set, only threads in the repositories it admits are written. A thread already read for a repository left out since is paused like the rest of its rows: it stays as it is, unless GitHub stops listing it, which archives it as for any thread (see below).

A scheduled run (never a webhook-driven one) reads `GET /notifications?all=true` for 50 threads a page and follows every page. It sends `If-Modified-Since` with the `Last-Modified` its last full read returned; a 304 answer writes nothing and does not count against the rate limit. It obeys `X-Poll-Interval` (GitHub sends 60 seconds): a run that comes sooner leaves notifications alone and says nothing. About once a day, or when the token or `GITHUB_REPOSITORIES` changes, it reads the whole listing without `If-Modified-Since`, which connects a thread to an issue, pull request or discussion synced since it was read.

A listing with `all=true` still holds what the person has read, but GitHub drops a thread marked done, and older threads age out of its retention. A listing sorted by its last change moves while it is paged, so one full read can skip a thread that is still there. A held thread is therefore archived only when two consecutive full reads of every page both lack it. The first read that lacks it keeps its id in the connector's saved state (the `missing` list), and the next run reads the listing whole, without `If-Modified-Since`, to confirm or clear it. A thread that is listed again leaves the list. A 304, or a failure on any page, leaves the list as it was and archives nothing. If GitHub returns an archived thread again, the row comes back.

## Transferred issues

GitHub gives a transferred issue a new node id, number and address, and copies its comments with new node ids and their old times. Its creation time, author, title and text stay. The old node id stops resolving, and the old address answers 301 with the new issue's address, or with an empty address when the App cannot read the repository the issue moved to. In the same installation, `issues.opened` arrives for the new issue and, about two seconds later, `issues.transferred` arrives for the old one and names both. A transfer into the installation from outside sends only `issues.opened`. GitHub records the transfer on the new issue's timeline at about the time it sends `issues.opened`, and the old address keeps answering as before for a moment. Either can come first, so a read made then can find no transfer on the timeline, or a transfer on the timeline while the old address still answers 200.

The connector keeps the Marfa row, so the issue keeps its Marfa ID, its comments and its connections to other rows. The proof is the old address answering 301 to the new issue's own address. The title is never compared, since either side may have been edited. The old row is found in one of three ways:

- The first read of an issue Marfa does not hold gets the transfer on its timeline in the same query that reads the issue. If the repository it came from is one whose rows Marfa holds, the connector looks there for a row created at the same time and asks the old address.
- A delivery that names the old issue and the new one, such as `issues.transferred`, asks the old address of the row it holds before the new issue is written, so the timeline does not matter.
- When the old repository is read first, its check of rows it no longer lists (daily, and whenever its listing changes) asks the old address and follows the 301.

A copy of each comment replaces the row of the comment it copies. The connector finds it by author, time and text. A row whose text was edited in Marfa is found by author and time alone, where exactly one row and one copy with that author and time are left once all the exact matches are made, so the order of the copies does not matter. Where more than one of either is left, which copy replaces which row is a guess, so none is matched: each copy becomes a row of its own. The comments of a moved issue are all read, because their copies keep the old times and no listing of what changed names them. A comment named alone by a delivery after its issue moved first asks its issue's old address. Where the issue moved to a repository the connector syncs and reads, the comment row follows its copy and keeps an edit waiting in it; otherwise the comment row is archived. The connector may follow that issue, but it archives the issue's row only if a delivery named the issue.

### A transfer in flight

The connector does not write an issue that may be mid-transfer, so it does not make a second row for it. An issue waits when all of these hold:

- Marfa has no row for it.
- Either its timeline shows no transfer, or its timeline shows a transfer from a repository whose rows Marfa holds and no such row's old address answers with a move to it yet.
- GitHub changed it within the last two minutes.
- It was created more than two minutes before that change, which a new issue, created and changed together, was not.

A waiting issue appears on the next run: the `issues.transferred` delivery that follows about two seconds later, or the next scheduled run. A scheduled run records the repository's issue listing as read, as for any other issue, and keeps the waiting issues in its saved progress with the time it first held each back. The next scheduled run reads them by node, writes one that proves to be a transfer as the row it replaces, and reads all its comments then. An issue that has waited a full window of two minutes since it was first held back, and has no proof of a transfer, is written as an ordinary new issue, however lately GitHub changed it, so a busy old issue cannot wait for ever. A run for deliveries keeps no such time: it leaves the issue to the next delivery or scheduled run. An issue transferred in from outside the installation has no `issues.transferred` delivery, so it appears on the next scheduled run. The two minutes are measured on the clock of the machine running the connector, against the times GitHub gives.

A rate limit does not let an issue through unchecked. A run for deliveries writes no issue that Marfa holds no row for if a rate limit stopped the read of the issue, which carries its timeline, or the old address's answer, or the read of a moved issue's comments, nor that issue's comments. The run reports that it is unfinished, and its deliveries are replayed.

### What happens to the item

- **Kept.** The issue moves to another repository the connector syncs and reads: the row keeps its ID, comments, connections and edits waiting in Marfa, and the edit is sent to the issue in its new repository. An issue transferred in from a repository outside the installation has no row to keep and is added once.
- **Kept as two items.** GitHub took longer than the wait to show the transfer, so the new issue was written as a row of its own. When the check then follows the old address to an issue that another row holds, the connector archives nothing and does not merge the rows. Both stay active, and a `duplicate:` condition, keyed by the older row, names both rows and says the issue was transferred. A comment copy that has a row of its own, while the row of the comment it copies is still there, is kept the same way, with a `duplicate:` condition keyed by the older comment row, and the daily check does not archive the comment rows of an issue whose row is still active and whose address answers 301. A person decides which to keep, and archiving the older row settles it: the next scheduled run clears the condition, and that of each comment pair, since a row a person archived is not raised again. Archiving the newer row does not: the older row cannot take the issue's node id while the newer row, archived or not, holds it, so the condition stays and names the newer row as archived.
- **Archived.** The issue moved to a repository the connector cannot read or does not sync, or the address no longer leads to the same issue. The row is archived, and an `issue-moved:` condition says which of these it was. Nothing is archived on a 404: an issue the old address does not know, in a repository that reads, is left as it is under `issue-missing:`. Both conditions clear at the daily check of the repository once the address no longer gives that answer.

## Setting it up

### Personal access token

Create a fine-grained personal access token for the repositories to sync, with Issues, Discussions, Pull requests, Commit statuses, and Contents read access, Starring read access to see the account's stars, and the automatically included Metadata read access. GitHub's form for a fine-grained token has no Checks permission, so the token cannot read check results: the connector then keeps each pull request's last `checks` summary, gives one read for the first time none, and names `checks-unreadable` once per run, and the other kinds sync as before. Commit statuses are not read on their own; they reach a pull request's summary only through the check rollup, which the token is refused. Set it as `GITHUB_PERSONAL_TOKEN` in the secret store and leave `GITHUB_APP_ID`, `GITHUB_PRIVATE_KEY`, and `GITHUB_WEBHOOK_SECRET` unset. The connector refuses mixed authentication settings.

Set `MARFA_API_URL` and `MARFA_API_KEY` as for the App, then run `node dist/main.js --once` or `node dist/main.js --every 1h`. No App, installation, webhook, or `--setup` is needed. A token `--setup <file>` invocation returns no new secrets, writes an empty JSON object to the requested file, and creates no inbound endpoint; the empty file may be deleted. Repository discovery uses GitHub's [authenticated repository listing](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user), including repositories owned by the user, collaborator access, and organization membership. `GITHUB_REPOSITORIES` narrows that list. Stars come from GitHub's [starred repositories listing](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user) for the same token. GitHub leaves out of the listing a star on a repository whose owner refuses the token, such as an organization with a policy on fine-grained tokens, so that star is not marked, and its row is never archived without the connector reading the repository first (see Starred repositories).

Personal token runs are always read only, even if the token has write permissions, and a token without Discussions read access leaves discussions unread while the other kinds sync. Edits to imported rows are restored from the agreed GitHub values. Creating or restoring a row never creates anything on GitHub. Changes arrive on the schedule. A token without Starring read access leaves stars unread while the other kinds sync. A rejected token fails the run and keeps existing rows and saved progress. A missing repository permission names the permission GitHub reports and leaves that repository's progress unchanged, while other repositories can finish; if every selected repository refuses permission, the run fails.

GitHub cannot narrow a personal token for one request as it can an installation token. Choose the token's repository access carefully: the read planner imports only the configured repositories, but relation reads can reveal addresses of other repositories the token can reach.

### GitHub App

A GitHub App, registered from the manifest the connector serves:

1. Mint the connector's key, as `template/README.md` says, with `--type-permission` for the eight types (`github.repository`, `github.issue`, `github.discussion`, `github.comment`, `github.pull_request`, `github.notification`, `github.file`, and `github.file.image`), `--edge-permission` for `github.in-repository`, `github.sub-issue-of`, `github.blocked-by`, `github.relates-to`, `github.duplicate-of`, `github.closes`, `github.closed-by`, `in-thread`, `references`, `attached-to`, and `parent-of` (the edge type the connector's `child-of` writes), `--metadata-permission types=write --metadata-permission edge_types=write`, and no `--permission`: `types=write` registers the types and keeps them current, and `edge_types=write` is needed to register connection types on first start and again when an upgrade widens their endpoint constraints. After registration or widening, the kit says how to narrow the key.
2. With `MARFA_API_URL`, `MARFA_API_KEY` and, where the instance has one, its public address as `GITHUB_PUBLIC_URL`, run `node dist/main.js --setup <file>`, naming a file outside the checkout and every other git working tree, such as one in the home directory: setup refuses a file in a folder that holds a `.git` or under one. Open the address it logs, continue to GitHub, create the App, named Marfa Connectors unless `GITHUB_APP_NAME` names another (GitHub holds each name once, so a second person's App needs its own), and install it on the repositories to sync from the address the setup logs next. For an organization's App, set `GITHUB_ORGANIZATION`.
3. Move the three secrets the file holds into the secret store and delete the file.

The manifest asks for the Discussions permission and the `discussion` and `discussion_comment` events. An App registered before Discussions came needs its owner to add the Discussions permission (read, or read and write) and the two events in the App's settings on GitHub, and each installation's owner to accept the new permission; until then the run names `discussions-unreadable` for each repository and the other kinds sync as before. Where `github.in-repository` and `in-thread` are already registered, the first start after the upgrade widens their endpoints, which is what the key's `edge_types=write` is for.

Without a public address the App's webhook is off, and the connector notices changes by polling alone. Run the setup again with `GITHUB_PUBLIC_URL` and the App's two secrets in the environment to point the App's webhook at the instance with a new secret, as when the instance moves. Each setup makes a new inbound endpoint, labeled with when it was set up, and names its id; retire the one it replaced with `marfa connectors endpoints retire <connector-id> <endpoint-id>`. A setup that fails retires the endpoint it made, or names it with the command to retire it by hand where the instance would not.

## Environment

- `GITHUB_PERSONAL_TOKEN`: a fine-grained personal access token, a secret. Use it alone, without the three App settings. Runs are always read only. It also lists the stars, and is used before `GITHUB_NOTIFICATIONS_TOKEN` for them.
- `GITHUB_APP_ID`: the App's id, required only for App runs.
- `GITHUB_PRIVATE_KEY`: the App's private key, a secret. Installation tokens are made from it for an hour at a time, each reaching only what it is for, as below, and kept out of every log.
- `GITHUB_WEBHOOK_SECRET`: the secret GitHub signs deliveries with, a secret.
- `GITHUB_NOTIFICATIONS_TOKEN`: a classic personal access token with only the `notifications` scope, a secret, optional. It works beside either the App settings or `GITHUB_PERSONAL_TOKEN`, and reads the notifications of the person who owns it; see Notifications. With no `GITHUB_PERSONAL_TOKEN`, it also lists the person's public stars; see Starred repositories.
- `GITHUB_READ_ONLY`: `true` for every kind, or a comma-separated list of `repository`, `issue`, `comment`, `discussion`, `pull_request`, `notification`, `file`, and `image`. With an App, a listed kind is read only and its imported rows' local edits are put back; other kinds can still carry changes. The `issue` setting also covers writable issue relations, including related issues; comments, on issues and on discussions, remain writable unless `comment` is listed too, and discussions unless `discussion` is. Duplicate connections are always read only. Repositories, pull requests, notifications and retained files are always read only. `false` or unset keeps App issues, discussions and comments two-way. Unknown kinds and empty list members refuse startup. Personal token runs stay read only with any valid setting.
- `GITHUB_STARS`: `true` (the default) or `false`, optional; anything else refuses startup. `false` turns off reading stars for this process: it lists none, asks GitHub for none, holds no `starred` or `starred_at` field, so it never writes or puts back a mark, and archives no repository row for a star, with no `stars-unreadable` condition. Set it to `false` on every process but one when several processes use one Marfa instance, since a star is a fact about the person and each process's token would otherwise list the same stars from its own view and unmark the rows the other process marked.
- `GITHUB_REPOSITORIES`: the repositories to sync, as `owner/repo` or `owner/*`, set apart by commas or spaces, in any case; optional, every repository the selected authentication method sees otherwise. A malformed entry stops the start.
- `GITHUB_PUBLIC_URL`, `GITHUB_ORGANIZATION`, `GITHUB_APP_NAME`: for the setup, optional. The public address's own path, where the instance sits behind a prefix, is kept before the webhook's.
- `GITHUB_API_URL`: optional, for a stub of the API; GitHub's otherwise. GitHub Enterprise Server is not tested.

The key and the run are as `template/README.md` says.

### Two tokens against one instance

To read repositories under two owners that one fine-grained token cannot both reach, such as an organization and a user, run the connector twice against the same instance, each process with its own token and its own `GITHUB_REPOSITORIES`, and with no repository in both lists. Each process needs its own Marfa key with its own source. The first key can use the connector's source, `github`; every later key takes `github-<account>` as its source and passes `--claim github`, as "One key per connector per account" in `template/README.md` shows. Set `GITHUB_STARS=false` on every process but the one whose token belongs to the person whose stars to read.

What the process that reads stars does to the rows the other process syncs:

- It sets only `starred` and `starred_at` on them, and leaves every other field to the process that syncs the repository.
- When a star is lost, it sets `starred` to `false` and never archives the row, since the row's `synced` is `true`. Only a row whose `synced` is `false`, one that a process stopped syncing while it was starred or one written for a star alone, is archived.
- A repository it starts to sync is marked `synced` by its own read. When it stops syncing one the other process still syncs, `synced` stays `true`.

These hold only with some limits:

- Every process must run a version of the connector that writes `synced`, and every key needs `types=write` once to add the field. A process on an earlier version still holds the star fields and puts back the marks the other process sets.
- A process removed for good leaves its rows with `synced` set to `true`, so a lost star only unmarks them. Archive those rows in Marfa if they are no longer wanted.
- A repository that moves from the process that reads stars to the other one can have its other read-only fields, such as `description`, put back by the first process, which still holds what it last wrote. The second process writes them again on its next run, so nothing is lost, but such a field can go back and forth between the two processes' runs. Give a repository to one process for good rather than moving it.

## Its tokens

Each installation token the connector asks GitHub for reaches no more than its use needs, naming repositories by GitHub's id, so a rename changes nothing:

- One lists which repositories an installation holds, and reads nothing else.
- One reads the issues, comments and pull requests of the repositories synced, and of those paused, so their relations stay. It also asks for check results, which a token without the Checks permission is refused; GitHub still answers the rest of the read, and only that installation's pull requests keep the check summaries they had.
- A classic token, `GITHUB_NOTIFICATIONS_TOKEN`, is a separate matter: it is sent to the notifications listing and, where `GITHUB_PERSONAL_TOKEN` is not set, to the star listing and the read of one repository that backs it, and never used for a write.
- One reads the Discussions of those repositories, with its own permission, so an installation that has not accepted the Discussions permission fails only this token, and only Discussions are left unread.
- One finds where an issue, comment or discussion named by a change sits, reading only, with the Discussions read permission for a discussion or one of its comments, across the repositories the connector holds under the installation. Where GitHub will not name one of them, as for a repository taken from the installation since the last scheduled run, or one whose id is not yet recorded, it reaches the whole installation instead; a change is still carried only into a synced repository.
- One for each change made in Marfa writes issues and comments only in the synced repositories that change touches: its own, and that of the issue at the other end of a relation it draws or removes. A paused repository is never among them. Where GitHub will not mint one, as for a repository gone from the installation since the last scheduled run, only the changes touching that repository wait. A change in a repository whose id is not yet recorded waits for the next scheduled run, which records it, and the run says so. A change to a discussion or to a comment on one asks for a write token that carries the Discussions write permission and no more. With `GITHUB_READ_ONLY=true`, or `issue`, `comment` and `discussion` all listed, no write token is requested.

GitHub names at most 500 repositories to a token, so past that many synced or paused under one installation, the token that reads reaches every repository of it, and the run says so; a token for a change names far fewer.

An installation token GitHub refuses after it was kept, as when it is revoked, is replaced and the request sent once more. A personal token is never replaced automatically: a 401 fails the run and names `GITHUB_PERSONAL_TOKEN`. Its REST and GraphQL budgets are tracked separately under a hash of the token, without retaining the token in a budget key.

A clock out of step with GitHub's by up to ten minutes is allowed for: what GitHub's answer says of its time is used to sign the App's requests from then on, and the look for a create whose answer was lost starts 15 minutes before that create was sent, so GitHub's clock being behind does not hide what it made. Past ten minutes the connector asks GitHub nothing, and each run says so until the clock is set right; a change made in Marfa meanwhile waits.

## Retained attachments

Images signed in GitHub's rendered issue and comment HTML are retained as `github.file.image` on `core.file.image`. Other signed assets use `github.file` on `core.file`. Each asset uses its immutable UUID and connects to its issue or comment through `attached-to`. An asset repeated in several bodies keeps all known parents. Parent and repository node IDs determine provenance; repository names are descriptive. Its `private` marker remains true while any known parent is private or its repository has unknown visibility, including after access is removed and a retained file is restored.

Downloads use HTTPS with no GitHub authorization, cookies, or referrer. Only `private-user-images.githubusercontent.com`, `objects.githubusercontent.com`, and the narrowly matched `github-production-user-asset-*.s3.amazonaws.com` hosts are allowed, including at every redirect. Downloads are limited to 25 MiB, four redirects, and 30 seconds; both declared and streamed lengths are checked. Signed addresses stay in memory and are never written into item properties or saved progress.

A failed or expired address is retried from fresh rendered HTML on a later run, even when the issue listing has not changed. The last good file is kept. A retained UUID reuses its blob receipt, so a changed signature or parent text does not redownload or upload the same bytes. Removing a link from GitHub does not delete retained bytes, and a file removed in Marfa is not recreated.

GitHub does not provide signed download addresses for some uploaded files. Their links stay in the original body. The issue or comment's read-only `github_files` object contains `repository_id` (immutable repository node ID), `body` (SHA-256 of the imported Markdown), `assets` (retained UUIDs), `pending`, and `not_kept` (stable addresses with safe reasons). File provenance in `github_parents` maps parent node IDs to `type`, `repository_id`, `repository` (descriptive name), and `private`. Unavailable asset UUIDs each remain pending for fresh HTML even when another asset in the same body succeeds. Unsigned upload URLs are accounted for in rendered links and visible text, including Markdown left as text after an HTML block. Attachment examples inside rendered code blocks are ignored. No placeholder file row is created without bytes. The connector does not use a signed-in browser or forward API credentials to download these links. Pull request bodies and Discussions are outside this attachment import.
