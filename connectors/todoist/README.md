# Todoist

Reads a Todoist account's tasks through the Sync API into `todoist.task` rows at the feed tier, and carries changes made in Marfa back to Todoist.

## What syncs

Every `todoist.task` on the instance syncs, whoever created it and under whatever source. The link between a row and its task is the property `todoist_id`: set from the sync for a task read from Todoist, and from Todoist's answer for a row created in Marfa, which becomes a task there. A task meant to stay in Marfa is a `core.task`, not a `todoist.task`.

A full sync, which a first run, a cleared state, a moved timezone, the connector reading a field or resource it did not read before, and Todoist answering a delta in full each start, lists only open tasks, so it is followed by the tasks completed in the last twelve weeks, and then each row still open in Marfa that neither list names is asked about by id, two hundred a run and the rest on the runs after, with at most two thousand held between runs and the rest asked at the next full sync: a task deleted since is archived, one completed earlier is read as completed, and one Todoist does not answer for the token is left as it is, asked about again each run and named by a condition until it answers or its row is no longer open. A run a change in Marfa starts, with the state lost, keeps no sync token, so the next scheduled run syncs in full. A row already completed in Marfa is not asked about, so one whose task was deleted while the connector was not following stays as it is.

What travels back: the title as `content`, the description (an empty one clears Todoist's), the priority (`low` to `urgent` as 1 to 4), the due date (a whole day as the date in the account's timezone, a timed one fixed in UTC in the task's own timezone, or floating where the task's time was, unless the clocks show that time twice, when it is fixed in the account's timezone, none clearing it; a recurring task keeps its recurrence, with the new date, a whole day or a time, as its next occurrence), the recurrence, and completion and reopening. A row made in Marfa is made in the project and section it names, with its labels, and in the Inbox where it names no project or its project is gone.

A change to a row's `labels`, `project_id`, `section_id` or `recurrence` reaches the task, and only a change: a field the row did not change is not sent, so an edit to another field never undoes a move made in Todoist, and a row that does not hold its task's recurrence yet never ends it. Labels are sent by name as a whole list, a name Todoist does not know is kept on the task as it is, an empty list clears them, and an order alone sends nothing. A move is sent last, after the edit and after a close or reopen, so a move Todoist refuses never holds a completion back. It has one destination: the section when it changed and the row names one, whose project the task takes; otherwise the project, outside any section, which is also where a cleared section sends the task. A row that names no project moves the task to none, though a cleared section still takes the task out of its section into the root of the project it is in. A subtask moved this way becomes a task of its own, as in Todoist, and its row follows without being put back. Todoist refusing a label or a move, as when the project or section no longer exists, is a condition naming the row, except for a task in the Inbox, where a missing project or section is where a create left it and nothing is raised. A recurrence is the task's due text in Todoist's own words, such as "every day at 2pm", read only while Todoist reads the due date as recurring. One the row sets is sent with the task's current date, or the row's new one, as its next occurrence, in the language Todoist reads the account's dates in: the one the account sets for date recognition, else its own, as a due words it (`pt_BR` is `pt`, `zh_CN` is `zh`, `zh_TW` is `tw`), and none for a language a due has no word for, such as `tr`, and a row holding a recurrence and no date takes the date Todoist gives it; one the row clears leaves the task due once on its current date. Sent with a date, text Todoist cannot read is kept as a task due once rather than refused, which would also end a recurrence the task had, so the task is read back, a recurrence it had is written back as it was on the date it holds, and the unreadable one is a condition naming the row, the other fields having reached the task. Sent without a date, as when a row makes a task, Todoist refuses the text, and the row is named the same way. Since the row holds the words but not their language, a recurrence worded in a language other than the account's is not read, and is named the same way. The parent and the order among siblings do not travel. An archive carries nothing. An edit to a row whose task Todoist no longer has is refused, and the sync that brings the deletion archives the row.

A trash in Marfa deletes the task in Todoist; closing it would not do, since Todoist closes a recurring task by moving it to its next occurrence. Todoist deletes a task with its subtasks, so trashing a parent row archives its children's rows when the next sync brings their deletion. A restore, or bringing back a row archived because its task was deleted in Todoist, makes the task again where Todoist no longer has it, as the row was, in its project and section with its labels, in the Inbox where its project is gone and at its project's root where its section is, completed if it was, and links the row to the new task; a recurring task comes back repeating, due when the row says, and a subtask comes back on its own; where Todoist still has it, the restore is carried like an edit. A purge after a trash changes nothing more: it sends the trash's delete again under the same command id, which Todoist takes once, and a trash and a purge made between two runs are one delete.

One Todoist account per instance for two-way sync. A second account's connector would create in its own account any row of the type without a link, and could not tell that account's task from one gone.

## Environment

- `TODOIST_API_TOKEN`: the account's API token, a secret.
- `TODOIST_API_URL`: optional, for a stub of the API; the real one otherwise.
- `TODOIST_READ_ONLY`: `true` for a read-only connector, optional. Nothing goes back to Todoist, and a change made in Marfa to a synced field is put back and named. A Todoist token cannot be narrowed to reading, so this is the only guard for a trial against a real account.

The key and the run are as `template/README.md` says.
