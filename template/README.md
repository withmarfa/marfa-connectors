# A new connector

A connector is a small folder: `src/main.ts`, what the connector is and what one run reads from its vendor, beside the type it writes and any helpers its vendor needs. The kit, `@withmarfa/connector`, does the rest:

- registers the connector on every start;
- refuses a key that holds more than its type needs;
- checks its type against the instance's, and adds a field it declares that the instance lacks;
- compares what the run found with the rows already written, and writes only what changed;
- heartbeats, keeps the connector's state, and reports each run;
- takes the webhooks a vendor posts, where the connector reads them.

## Start one

1. `cp -R template/connector connectors/<name>`, and set `name` in its `package.json` to `<name>`. The folder sits at a connector's depth, so its paths hold once copied.
2. Add `{ "path": "connectors/<name>" }` to the references in the root `tsconfig.json`. Until it is there, the tree test fails `pnpm test`, since the build would skip the connector.
3. Replace `src/example.item.json` with the type the connector writes, and in `src/main.ts` name the connector, its source and its `types`, each a type with the `fields` the vendor holds, declare the environment it needs, and write `run`. A connector may write up to ten types, such as issues, comments and files, each with its own fields, read-only fields and link. Where the vendor's rows read as a core type, such as a task or a bookmark, the type names that core type as its `parent` and adds only the vendor's own fields, and `run` writes the core type's fields under the core type's names; `compatible_with` is not used.
4. `test/connector.test.ts` runs the example as a process against a scripted server and a stub vendor. Rewrite it for yours.
5. `pnpm install && pnpm build && pnpm test`.

What a run has to hand:

- **`upsert(type, entries)`**: each entry is a `source_id`, its properties and its `occurred_at`. Put the vendor account inside the `source_id`, as `<account>:<id>`, so two accounts under one source never share a row. A property that is absent or `null` is cleared from the row. Every property an entry carries is among its type's `fields`, the properties the vendor holds; an entry carrying another is refused with a condition. A row's other properties are Marfa's own and never touched. A row the instance refuses is held with a condition naming it and the instance's reason, and the run goes on; the next run that reads it writes it again. A row a person retyped, to a type the key may not write or to another of the connector's types, cannot be mended by writing it again, so its condition stands for as long as the vendor names the row, and it holds back nothing else. A refusal every write would meet fails the run instead: an instance that does not answer, a key it refuses or one narrowed so it no longer writes the connector's types, the connector's own source refused a create of its type, or every row one call wrote refused alike.
- **What the vendor changed, field by field.** For each row the kit keeps, on the instance, what each side last held, field by field. An entry is written only where the vendor changed something since, and only the fields it changed: an edit made in Marfa to another field stays. A field both sides changed goes to the later change, by the entry's `changed_at` and when the edit was first seen in Marfa, and a tie to Marfa; the run names the row and the field that lost. An entry older than what the two sides last agreed on is left unwritten. A row that nothing was agreed for, as after the connector's state was cleared, takes the vendor's value wherever the two differ, and the run says how many.
- **`archive(type, keys)`**: for what the vendor deleted, by natural key, or by the vendor's id where the type names a link. A row is archived, never trashed, and a row a person trashed is never touched. A row archived this way comes back when the vendor sends it again; one a person archived stays archived.
- **What a run reads.** Only the rows its entries, the log and the changes waiting name, looked up by link, natural key or id in every state; the type is listed whole only when the log no longer holds the cursor.
- **`connections`**, on the connector, with `connections` on an entry: kinds of connection between the connector's own rows, such as an issue's sub-issues, each an edge type as `POST /edge-types` takes it, both ends constrained to the connector's types, orphaning on delete, and requiring no property, since the kit writes none. The kit registers each on the first start and refuses to run where the server's differs. An entry's `connections` names, for each connection type, every row its row points at, by type and by link, or natural key where the type names no link, and an empty list where there is none; a type left out is left as it is, and one never named has nothing agreed, so a change made to it in Marfa is not carried. They are written once the run's rows are, so a target made in the same run is found, and one Marfa does not hold yet is connected when it arrives, whether or not the vendor names it again. A connection made or removed in Marfa is carried to `onChange` as `change.connections`, the rows at the other end, or put back where the row's type is read only; one a purge took is never carried, and one from the connector's row to a row outside the declared ends, such as a person attaching a file to their own note, is theirs and left alone. Where nothing is agreed for a type, as after the connector's state was cleared, the vendor's set is taken and nothing carried.
- **`file`**, on an entry of a file type: a type whose `parent` is `core.file` or one beneath it, whose `fields` list `blob_ref` and `mime_type`. It gives the vendor's own key for the bytes, such as an etag or asset id, and `load`, which fetches them, whole or as a stream such as the vendor's response body; a stream is uploaded as it is read, never held whole, and the upload is cut off only when it goes quiet for the request time limit, never for its length. The kit loads and uploads the bytes only when that key differs from the one it last uploaded, in the run that writes the row, and writes the answer as `blob_ref` and `mime_type`; the instance then reads text and image dimensions from them. Bytes the vendor would not give, or a stream of them that breaks or goes quiet, are a condition, and the row waits; an upload the instance refuses, such as a file of no bytes, holds the row as any refusal of it does. A file attaches to its item through the instance's own `attached-to`, declared among `connections` with both ends narrowed to the connector's types; the kit never registers it, and the key holds `--edge-permission attached-to=write`. A message joins its thread the same way, through the instance's own `in-thread`, such as a comment on its issue. The kit writes no `position` on it, so the thread's order is the messages' own time, and since a message is in one thread, one a person put in a thread of their own is left there and the vendor's thread refused, with a condition.
- **A purge is remembered by the instance.** An entry naming a row a person purged is not written back, however long after and whatever the connector's state, until the vendor changes it after the purge; it then comes back as a new row. The run says how many entries it held back.
- **`linked(type, connection, target)`**: the active rows of a type holding a connection of that kind to a row the target names, such as a repository's issues, read from the instance: what Marfa holds under something, so a connector can find what its vendor no longer lists and ask the vendor about each. Only rows of the type itself that the vendor has been told about are answered. Connections the run's own entries name are written once it ends, so a row they connect shows from the next run, and one they move elsewhere, such as an issue moved to another repository, is left out at once.
- **`derive(type, keys, values)`**: sets a type's `derived` fields on the rows held under these keys, by natural key or the vendor's id as `archive` takes them, where the vendor's answer is not to hand, such as for a container no longer readable. It writes only what differs, never to a row in the bin, and agrees the value so it is no change on the next read.
- **`held(type)`**: the active rows of a type the vendor has been told about, read from the instance, whatever their connections: what Marfa holds of the type, for a vendor whose listing leaves out what it deleted, such as one that lists only open items after it lost its place, so the connector can ask the vendor about each row its listing left out.
- **`written(type)`**: the fields of the type the kit writes now, which are the `fields` the connector declares for it, less any the key may not add to the server's type (see below), so it changes when that narrowing begins or lifts. A connector that reads by delta, such as with a sync token, brings a field onto a row it already holds only when the vendor changes the row, so it should include these fields in whatever marker makes it read in full.
- **`state.get` and `state.set`**: a small value kept between runs, such as a sync token. It is kept on the instance, under the key's own source, and only when every write in the run landed, so a connector needs no disk of its own and can start anywhere, empty.
- **`forScope(name)`**: bind row calls to one read scope without adding stored scope fields. Await each scoped operation serially. Two unfinished scopes touching the same item cannot checkpoint; finish one before the other changes that item. Root calls may run concurrently and their shared operations are queued. Mixing root calls with an active scoped operation is refused. An operation or checkpoint left in flight when `run` returns fails the run.
- **`forScope(name).state.get(key)`**: a detached value from the last acknowledged vendor state, including checkpoints completed earlier this run. It does not read the mutable root draft.
- **`forScope(name).state.checkpoint(key, value)`**: explicitly await a JSON-compatible candidate after completing that scope's read. The kit clones it, drains that scope's connections, acknowledges its prerequisite agreements, then replaces the existing full state envelope through the same fenced door used at the end of a run. Applicable edges must land first; absent targets must be durably named in the existing pending connection agreement. A completed checkpoint survives a later failed scope or process restart. The API replaces the explicit JSON value; it does not merge vendor fields. When scopes share a map key, build each candidate from that scope's latest acknowledged `get(key)` plus only its completed entry. Reusing a run-wide speculative map could wrongly save an earlier blocked scope's validator. It keeps the last acknowledged log cursor and standing conditions; it neither clears conditions nor rotates a report mid-run. Ordinary row and edge writes are not a transaction and may already have landed when a checkpoint fails, so replay remains necessary.

  The awaited result is `{ committed: true }` or `{ committed: false, reason }`. Blocking reasons are `row-refused`, `agreement-skipped`, `agreement-oversized`, `connection-unresolved`, `scope-overlap`, and `state-oversized`. A nonterminal row refusal blocks even if its usual final-only handling counts no held row. Skipped agreements block conservatively without querying whether the item was hidden or purged; oversized agreement intentions remain pending rather than being cleared. An unrelated scope can still checkpoint. No refusal journal or automatic cursor is created. Non-JSON input, transport failures, malformed acknowledgments, lost holds and concurrent scoped use throw. Checkpoints require a successfully loaded state and an active full vendor read; a hinted read cannot advance whole-source progress.

  The entire state envelope must fit 512 KiB and each required agreement 16 KiB. A clear acknowledgment counts agreements actually deleted, so an accepted clear of a readable item without an agreement correctly returns zero. If a state response is lost or ambiguous, every later mutation and final save stops: the server may have committed it, and sending an older envelope would roll progress back. The next process reloads authoritative state. The existing root `state.get/set` API still saves its draft only when the whole run's writes land; a later failure falls back to the latest acknowledged checkpoint.

- **`log.condition(key, message)`**: something that lasts across runs but lets the run go on, such as a feed that stopped answering among several. Raise it on every run it holds: the kit warns it in the log and carries it in each run's report while it stands, and logs it as cleared once a successful scheduled run reaches its check without raising it. A run that failed, or that deliveries started, clears none, and its report carries what stood before beside what it raised. A report has room for about two thousand characters: the conditions that do not fit are counted in it, named in the log, and carried first in the next report. A run in which the connector read nothing, because every source it reads failed, is thrown as a failure rather than left to succeed with conditions. What stops the run, such as a vendor refusing the token, is thrown instead, and fails the run.
- **`log.unreached({ keys?, prefixes?, exceptKeys? })`**: mark the exact checks skipped this run, using exact condition keys or literal key prefixes. Existing matching conditions stand through a successful scheduled run; a reached check that finds the problem gone can clear it on a later run. Calls accumulate for this run alone. `exceptKeys` excludes exact keys from that call's prefix matches, so a connector can preserve a family with unknown identities while naming the checks it actually reached. Exceptions do not cancel exact `keys` or another call's selectors. Keep unknown identities conservatively when saved progress cannot enumerate every standing condition. Selectors do not raise a condition, create stored state, or override a newly raised message. For example, skipping a feed's access check calls `log.unreached({ keys: ["feed-gone:" + feedId] })`; still raise lasting problems with `log.condition` whenever their checks find them.
- **`signal`**: hand it to `fetch`, so a stop is prompt.
- **`env`**: the values the connector declared. A `secret` or `required` value that is missing stops the start, and a secret never reaches a log line or a report. A secret that holds a list, such as several addresses, is also kept out part by part, where each part is set apart by whitespace or commas and is at least eight characters long. A value the connector can tell is wrong on sight, such as a malformed address, is refused by throwing from `checkEnv`, which stops the start the same way.
- **`secret(value)`**, in `run`, `onChange`, `remake` and `setup`: keeps a value made at run time, such as an installation token, out of every log line, condition and report from then on. A value under eight characters is refused, since it could not be found without redacting ordinary words.

A connector writes only its own type at the feed tier. Promoting a row into the library is a person's or an app's act. A connector reads from its vendor; one that is asked to also carries changes made in Marfa back to it, as the next section describes, and never anything else.

## Carrying changes back

Before entering a vendor read, the kit acknowledges pending agreements from its watch observations and completed early carries. An acknowledgment removes ownership only for the exact intent the server accepted. Ordinary outbound field edits still run after the vendor read so they can reconcile with its values. Durable waiting and refusal intent remains in the agreement; acknowledging it does not mean the vendor accepted the change. An unusable prerequisite acknowledgment, including a skipped or oversized intent, a malformed answer, a refusal or a lost response, stops the reader and prevents later agreement retries or state/cursor saves in that process. A new process reloads what the server actually kept.

A two-way connector declares two more things, and the kit's watch phase does the rest:

- **`link_field`**, in each type's definition: the property that holds the vendor's own id for a row. The instance keeps it unique within the type, in every state, and refuses a second row holding the same value with `link_taken`. With a link, every row of the type is the connector's to read and write, whoever created it and under whatever source: an entry finds its row by the link first and by its natural key second, `archive` takes the vendor's ids, and a row carrying no value is one the vendor has not been told about. A row counts as told only once the connector and the vendor agreed on it under the value it carries, so a row made by hand with a value of its own is never taken for one the vendor has: a connection to it waits, and `linked` leaves it out. Every entry `run` hands over carries the link; one without it is refused with a condition. The link is the connector's: a person's change to it is put back, with a condition, before anything is carried by it. A row in the bin cannot have it put back, so its change is carried by the link agreed with the vendor. A purge drops what was agreed, so the kit carries one only by a link it can vouch for: the agreed one, which it keeps from the moment a run reads a link other than it until the agreed one is written back, for up to a thousand rows, or the row's own where every change the run read for the row since then moved it between states, or was the connector's own create, and showed the same link. Any other purge is not carried, and the run names the row; past the thousand, no purge goes by the row's own link until a whole read of the log keeps every such link again. The example names `example_id`. A type registered before it named its link fails the start until it is replaced with one that does. Say so in the connector's own README: a row of the type made by hand is carried to the vendor, and something meant to stay in Marfa is a row of the core type instead.
- **`onChange(change, context)`**: called once per row with something in Marfa the vendor has not had, with `change.kind` one of `created`, `updated`, `restored`, `archived`, `trashed` or `purged` (a restore's `change.was` saying whether from the bin or from archive), `change.item` the row as it stands, and `change.changed` the fields changed in Marfa and not yet carried, the read-only ones and the link left out. A transition carries the fields changed beside it; a trash and a purge carry none. What of a row travels is the connector's choice; the example sends the title, url and note. It may answer the vendor's entry as its write left it, which the kit takes as what the vendor now holds, so a value the vendor normalizes, or its own close echoed back, is no change; without an answer the carried values are taken as the vendor's. An answer is written onto the row for each field it states, a null as a clear, that the change did not carry and Marfa has not changed since, or that is read-only, such as the number a vendor gave a row it just made, or its reopening on a restore; a field the change carried keeps the person's value. An answer's `connections` are what the vendor holds for each type it names, so a connection the vendor would not take, such as one past its limit, is taken back in Marfa once the run's carries are done; the connector says why with a condition. For a purge, the answer's `changed_at` keeps the purge remembered past the vendor's change carrying it made, such as a close where the vendor cannot delete. `context.setLink(item, id)` writes the vendor's id onto a row the vendor just made, retrying once if the row moved since, and throws `LinkTaken` for a value another row carries; the example takes that as a refusal. Resolving means the vendor took the change, or there was nothing to send: the kit then takes the carried values as the vendor's, so a handler never resolves after a write the vendor did not take, and never answers one with only a condition. A change the vendor did not take is thrown as `Unreachable` or `Refused`, and either way nothing is agreed, the row keeps the person's values over the vendor's next read, the run goes on, and a condition says why until the change lands; a change the vendor is not to take at all is thrown as `Declined`:
  - **`Unreachable`**, for an answer that can pass by itself, such as a rate limit, a server error, a timeout or no answer: the change is sent again next run. Give it a message naming the row; where many rows can wait on one part of the vendor, such as one account, pass that part as `scope` and a message naming it instead, and the changes waiting on one scope raise one condition between them, saying how many wait.
  - **`Refused`**, for an answer that will not change by sending again, such as a value the vendor rejects or a row the account may not change, with the vendor's reason as its message: the kit names the row beside it. The same change is not sent again, so the vendor is not asked the same thing every run; once the row changes in Marfa, by a person or by the vendor's own read, what differs is sent. A refused edit is sent again once a carried field changes, a cleared one included; a refused trash, which carries no field, only once the row is restored. A purge, which cannot change, is asked again a day after its refusal, and its condition stands meanwhile. While a refusal stands, `change.refused` marks it: a refused write made nothing, so a create sent after one takes an idempotency key of its own from it, where a key kept across a lost answer would have the vendor answer the refusal again. The reason kept with the row is cut to 200 bytes, and dropped where the row's agreement has no room for it beside the refusal; where it has no room even for the refusal's mark, which the instance's cap on one agreement decides, nothing is remembered, and the change is sent again each run, as its condition says.

  - **`Declined`**, where the vendor is not to be asked at all, such as an edit to something another person wrote there, with a message naming the row: the fields the change carried are put back to what was agreed, the row's state stays as Marfa has it, the message is raised as a condition, and nothing is tried again until the row changes again.

  Any change may carry `change.unagreed`, the read-only fields the row holds otherwise than was agreed with the vendor, where putting them back failed: none of them is the vendor's, so a decision taken on one waits.

  Any change may also carry `change.placement`: for each connection type the vendor holds read only, such as the repository an issue sits in, the rows the agreed connections name, as the vendor was told of them. It says where the row sits as agreed with the vendor, never what a person drew since, so a decision about where to write or whether to wait is taken on it rather than on the row's own text.

  What stops every change, such as a vendor refusing the token, is thrown as any other error and fails the run; the change waits for the next. The example sends a 429, a 5xx or no answer as `Unreachable` and any other refusal as `Refused`. Where a create is sent again after a try whose answer was lost, the vendor answers with what that try made, from the values the row held then, so the example links the row to that item first and then sends what the row holds now over it, so a refused update leaves a linked row and the next change goes out as an edit.

- **`readOnly`**, optional, on each type: fields the vendor holds that are never carried back. Marfa mirrors them: a change made to one in Marfa is put back on the next run, from what the connector last wrote, and the run names the field. Every field is read-only for a connector without `onChange`, or for a type its `carries(env)` leaves out, so any kind can run read only; and the link is read-only for every type. It may also name connection types from the type's rows that the vendor cannot change that way, such as the repository an issue sits in: Marfa mirrors them as it does a read-only kind's, putting back a change and naming it, but a create, and `remake`, are handed them in `change.connections`, since they say where the row goes. A create waits until the vendor has been told about each row they name, within the same run where that row is made in it, and the run names a create still waiting.
- **`revive`**, optional, on each type: a row in the bin comes back when the vendor changes it, once its trash has reached the vendor, and the run names it; a change only in a `derived` field is not such a change. It comes back as the vendor has it, its close among the fields, where Marfa had not changed them. A trash still waiting to be carried is never undone this way. Carrying the trash must answer the vendor's entry, or the vendor's own close reads as a change and brings the row straight back.
- **`derived`**, optional, on each type: read-only fields that say where a row sits, not what happened to it, such as its container's visibility. A change in one is never the vendor's activity: it brings no trashed row back, and a field an agreement never held is no change. A row in the bin is left alone, so it takes the value when it comes back.

Every entry `run` hands to `upsert` should carry `changed_at`, when the vendor last changed it: it is what the conflict rule reads, and a vendor naming no time loses every conflict.

- **`remake(change, context)`**, optional: makes a restored row again at a vendor that no longer has it, links the row to what it made, and answers whether it did. It is asked for every `restored` change before the vendor is read; a row the vendor still has answers `false` and is carried by `onChange` after the read. It answers `true` only once the vendor has made the row and it is linked: a remake the vendor did not take throws `Unreachable`, `Refused` or `Declined` as `onChange` does, and is asked again by the same rule. Where a remake failed before, `change.attempted` says when it was first asked, so what it made then can be found. The example asks the vendor for the item and makes it again on a 404.

How a run goes: the log is read, and each row it names is compared with what the two sides last agreed on; what differs is recorded as waiting, from when it was first seen, before the log's cursor moves past it, so a run that fails, or a process that stops, loses nothing still to carry. Creates are carried, and restored rows offered to `remake`; `run` pulls and writes what the vendor had; the rest of what waits is carried; the state is kept, and then the run is reported. A create goes before the vendor is read, because a run that failed between the vendor's answer and the link would otherwise read the vendor's copy first and create the row's twin. The kit records a create before sending it; where one was sent and no link came back, `change.attempted` says when it was first sent, so a connector whose vendor takes no idempotency key can look for what it made before making another. Where a create made the vendor's object and linked the row but the run then failed, nothing was agreed for the row's fields, so the next change is an update with every field the vendor has not since sent back in `changed`, and `change.made` says when the create was first sent; a connector whose create took fields sends one of them only if it differs from the vendor's object. The report's `pushed` counts every change carried, landed or abandoned; `own` counts the log's frames showing a row as the connector last left it, which are its own writes; `conflicts` counts each row where a field was decided by the later change.

A trash in Marfa wins over the vendor: a trashed row is never written, unless its type revives, and the trash is carried. An archive in Marfa touches no field and travels beside whatever the vendor sends. A restore is carried as a restore, made again at a vendor that no longer has the row; where a trash deletes at the vendor, a change there after the restore means the vendor has the row again, and where it only closes, as for a type that revives, the restore still reopens it. A row the vendor deleted is archived, and a person's restore of it since is not undone by the vendor's next word. A purge is carried once, kept on the instance until it lands, so a run that fails first loses none; one the log no longer holds, as after a long time offline, is remembered but not carried; the example sends the trash's delete again, which a vendor that took it answers as already done, and which still deletes where a trash and a purge made between two runs reach the connector as the purge alone. A row another row's trash took into the bin, through a connection that cascades, is not the person's trash of it: its trash, its restore and its purge are not carried, and a field changed before it waits for the restore.

A connector without `onChange` reads the log too: a change made in Marfa to a field it mirrors is put back from what it last wrote, on the next run, and the run names the field.

## Receiving webhooks

A vendor that posts webhooks, such as GitHub, can tell the connector what changed rather than wait for its schedule. The instance stores each delivery as it arrived and never reads it; the connector declares how to read one:

```ts
inbound: {
  // The vendor's signature over the body exactly as it arrived.
  verify: (delivery, env) =>
    verifyHmac({
      secret: env.EXAMPLE_WEBHOOK_SECRET,
      body: delivery.body,
      signature: delivery.header("X-Signature"),
    }),
  // What the delivery says changed, as ids `run` can fetch.
  hints: (delivery) => [
    {
      type: "example.item",
      id: String(JSON.parse(new TextDecoder().decode(delivery.body)).id),
    },
  ],
},
```

- **`verify`** answers whether a delivery came from the vendor. `verifyHmac` from the kit compares an HMAC in constant time: `prefix` for a header such as GitHub's `sha256=…`, `encoding: "base64"` for a vendor that signs in base64. The secret is declared in `env` as a `secret`, so it never reaches a log line. A delivery that fails, or whose `verify` throws, is marked rejected for good and changes nothing, and the run says how many with a condition, which usually means the secret differs from the one the vendor signs with. Keep `verify` to the delivery and the environment: a check that reaches the network can fail for a passing reason and reject a genuine delivery. It is handed a signal that aborts on a stop or after ten seconds; a check still running then leaves its delivery waiting for a later run, with a condition, and the deliveries behind it are taken.
- **`hints`** answers what the delivery says changed, as the type and id of each thing `run` fetches, or `"everything"`. A `hints` that throws, as the example does on a body that is not JSON, means everything, and the run says how many with a condition; neither error's text is kept, since it can quote the body. A delivery is a hint, never the vendor's state: the vendor may send them out of order, twice, or not at all, so `run` always fetches what the hint names and writes that.
- **`run`** reads `context.hints`. It is `undefined` on a scheduled run, which reads the vendor whole, and on a run whose deliveries asked for everything; otherwise it is, by type, the ids the deliveries named, which may be empty, and the run fetches only those and leaves any cursor into the vendor, such as a sync token, where it was, since the rest was not read. Both write through `upsert` and `archive`, so a delivery and the schedule reach a row the same way.
- A run the deliveries started clears no condition, having checked only part, and reports those that stand.
- A connector with `onChange` is handed, beside what the deliveries named, the links of rows with a change in Marfa still to carry, so the run reads what it will write over. A field changed in Marfa is carried only over a row whose entry the run read; the rest wait for the next run that reads them, and the scheduled run reads the vendor whole. A run for deliveries archives only what it was handed, since the rest of the vendor was not read, and with more than two hundred rows waiting it reads the vendor whole.

How deliveries are taken:

- Every run first collects what waits at the connector's endpoints, up to five hundred, fetching each body to verify it. A body that cannot be fetched leaves its delivery waiting for a later run, with a condition, and the rest are taken. A verified delivery that repeats one already processed, or one verified earlier in the same collection, by the header the endpoint names, is marked a duplicate.
- A delivery is marked processed once the run that took it ends without error. A write the run held does not keep it waiting, since the next scheduled run reads the vendor whole and writes it again; a run that fails leaves it waiting for the next.
- A scheduled run that cannot read the deliveries or the endpoints says so with a condition and still reads the vendor whole.
- With `--every`, the kit looks between scheduled runs, every ten seconds or as often as `--look-every` says: for a waiting delivery, for a change in Marfa its vendor has not had, where the connector has `onChange`, and for a change in Marfa to a field it mirrors, which it reads from the log and tells from its own writes. Any of them starts a run for it at once, so a change made in Marfa reaches the vendor, or is put back, within a look rather than at the next schedule. A run that fails, or whose deliveries could not be marked, leaves what waits for the scheduled run rather than trying again at every look. The schedule stays the safety net, since a vendor does not promise to deliver: GitHub does not retry a failed delivery. `--look-every` is refused for a connector that neither receives webhooks nor carries changes back.
- Each run's report counts the deliveries it processed, rejected and marked duplicate.

The address comes from the instance, never from the kit. With the connector registered, make an endpoint with its own key or the operator key:

```bash
marfa connectors endpoints create <connector-id> --label <vendor> --duplicate-header <header>
```

The answer carries the address in full this once, as `path` and as `url`, the address the binary reached joined to it; later reads show only its last four characters. Give the vendor the instance's public address with that path, and the secret it signs with. `--duplicate-header` names the header a vendor repeats on a redelivery, such as `X-GitHub-Delivery`. A scheduled run whose registration holds no live endpoint says how to make one. `marfa connectors endpoints retire <connector-id> <endpoint-id>` stops an address answering. `marfa connectors deliveries list <connector-id>` shows what waits, with the connector's own key only: the operator key is refused, as on every read of the connector's data.

## The key

One key per connector per account, minted with the `marfa` binary by a credential that holds `keys.mint`:

```bash
marfa keys create --label <name> --source <name> --type-permission <type>=write --metadata-permission types=write --default-tier feed
```

- `--source <name>`: the connector's source, which every row it writes carries.
- `--type-permission <type>=write`, once for each type the connector writes: reach on its own types and on nothing else.
- `--edge-permission <connection>=write`, once for each connection type, and `--metadata-permission edge_types=write`, for a connector that registers connection types of its own, which needs write on each id and any reverse name in its edge map; `attached-to` and `in-thread` are the instance's and need only the first.
- `--metadata-permission types=write`: lets it register its type on its first start, and again should the type be deleted from the instance, and lets it keep the type current, adding a field a later version of the connector declares, as [When the connector's type changes](#when-the-connectors-type-changes) says. Its type map bounds it to the connector's own types.
- `--default-tier feed`: puts what it writes in the feed.

Naming the maps, the key holds no permission: it cannot mint keys, purge, delete a type, or change the instance's settings, and it reads and writes no other type's rows. The key holds no `schema.write`, which would let a leaked key delete the connector's types. Its type map confines `types=write` to the connector's own types: it registers a type only under an id the map grants write on, and replaces one only within what the instance allows a key without `schema.write`, as below. The kit reads the key back on every start (`GET /keys/current`) and refuses to run on one that holds any permission, `schema.write` included, or more than read and write on its own types and connections and write on `types` to register them and keep them current (and on `edge_types` for connection types), or that may not write each of them, naming the key and what is too wide or missing, before it registers a type or writes a row; the refusal is the registration's failed run. It refuses as well a key whose own source is not the connector's and that does not claim it, a key claiming any source besides the connector's, and a key an app made, saying for each what to change. A key minted naming nothing, which takes the minter's whole set, is refused, and so is one minted before an instance gave a key named with maps no permission beside them. Revoke such a key with `marfa keys revoke <id>` and mint another as above; its source is free again once it is revoked. The revoked key's registration stays, with its failed run, until `marfa connectors delete <id>` removes it.

The key keeps `types=write` for as long as the connector runs, since it is how the connector keeps its types current and registers one that is deleted from the instance. Once every connection the connector declares is registered, it has no use for `edge_types=write`, and the kit warns on each start while the key still holds it. Narrow the key in place with the operator key:

```bash
marfa keys update <key-id> --metadata-permission types=write --metadata-permission edge_types=read
```

Read on `edge_types` registers nothing, and the binary names a map only with its entries, so read is how it narrows one. An update replaces a whole map with the entries it names, so the command names `types=write` again: without it the key would lose the write that keeps its types current. The rest of the key stays as it was. A later version of the connector that declares a new connection type needs `edge_types=write` again until its first start has registered it.

"One key per connector per account" means a second account's key carries its own source and claims the connector's. A key's own source is unique among live keys, so the second key takes `<name>-<account>` as its own and claims `<name>`, which the kit names on every write:

```bash
marfa keys create --label <name>-<account> --source <name>-<account> --claim <name> --type-permission <type>=write --metadata-permission types=write --default-tier feed
```

Mint the key with the operator key. A working key can pass on only the sources it writes under itself, its own and its claims, so even one holding every permission is refused `<name>`; it can pass on only the map entries it holds, too, so one holding `keys.mint` without `types=write` in its metadata map is refused the key's `types=write`. The operator key is exempt from both, which is how a claim starts. The two keys then write under one source, each account's rows kept apart by the account inside the `source_id`, and each keeps its own state on the instance, under its own source. For a connector that carries changes back, one account per instance: a row of the type without a link would be created in whichever account's connector ran first, and the other could not tell that account's item from one gone.

### When the connector's type changes

On every start, the kit reads each type the connector declares from the instance and compares it with the one the connector carries.

- **A field on the instance that the connector does not declare** is kept, and is no difference: an operator or another version of the connector added it. A field the instance requires that the connector does not declare is a difference, as below.
- **An optional field the connector declares that the instance lacks**, such as one a later version of the connector adds, is the one difference the connector puts right itself. With `types=write`, it replaces the type with its own definition, keeping the fields, version, version policy, roles and merge policy the instance already holds; reads the type back; logs the fields it added; and starts. The rows the type already holds keep their values until their next write. A replacement the instance refuses for another reason stops the start with the instance's reason, and one read back still different stops it too, since another process may be changing the type; neither is tried again.
- **Where the instance does not allow the key the change**, the connector starts without those fields: it writes nothing under them, so the rows keep whatever they hold there, and each run raises a condition naming the fix. The instance lets a key without `schema.write` add only an optional field whose name no stored row of the type or of a type inheriting from it holds a value under, and change the label, description, display hints and version, and the description of a field the type keeps. It refuses every other change, naming the members that need `schema.write`: the condition then names them and says an operator replaces the type with the connector's definition, `marfa types update <type-id> --file <definition>`. This covers a field name that rows still hold from before an operator removed it, and a type that holds as its own a role, version policy entry or merge policy entry that its parent also provides, since the replacement sends only what the parent does not. A key without `types=write` raises a condition naming the command that grants it, `marfa keys update <key-id> --metadata-permission types=write`, with a `--metadata-permission` for every other metadata entry the key holds, since an update replaces the whole map. Under `--every`, each scheduled run reads the key and the type again, so granting the permission, or an operator replacing the type, lifts this without a restart, and a check that finds any other difference stops the process with exit code 1, as at start. The link field, `blob_ref` and `mime_type` are the exception: the connector cannot write its rows without them, so it does not start.
- **Any other difference in a type stops the start**, naming each difference and the operator's command: a changed link field or parent, a field made required or given another shape, and a required field the instance lacks or the connector does not declare. An operator who means the change replaces the type with the connector's definition, `marfa types update <type-id> --file <definition>`; the rows keep their values until their next write. So two versions of a connector running against one instance never rewrite each other's type.
- **Any difference in a connection type stops the start**, naming each difference. The kit never replaces a connection type, and the instance has no door that does.

## Run it

The environment is `MARFA_API_URL`, `MARFA_API_KEY` and whatever `env` declares. The connector keeps no file: its state is on the instance, and `--setup` writes one only for the person to move.

- **`node dist/main.js --once`**: one run, then exit, for launchd, cron or a scheduled container. Exit codes: `0` for a run that succeeded or a clean stop, `1` for a failed run or a start that could not complete, `2` for a missing or malformed setting. A run cut short by SIGTERM or SIGINT is not reported, since a run's outcome is only succeeded or failed: the log says it stopped, and what it had already written and agreed is kept, so the next run carries on from it. The connector's state is saved before the run is reported, and a save the server refuses, such as one past its 512 KiB cap on the state, fails the run, so a run never reports success while its progress stands still. The state holds the connector's own, the log's cursor, the standing conditions, at most two hundred, each cut to 500 characters, and the purges still to carry, each kept until it lands at the vendor.
- **`node dist/main.js --every 15m`**: a long-lived process. Runs never overlap, and the heartbeat has its own one-minute timer. A failed run is reported, and the next waits twice as long, up to eight intervals, or as long as a refusal's `Retry-After` names if longer. A run that failed because Marfa did not answer is asked about instead: the connector checks Marfa every 15 seconds or the interval if shorter, a little spread so connectors do not arrive together, and runs again once it answers; if that run fails for Marfa again too, the backoff applies, until a run succeeds or fails for another cause, which re-arms the quick retry. A key the server refuses, or one narrowed so it no longer writes the connector's types, stops the process with exit code 1. Exit code 2 is for an address that cannot be used: at start, a redirect, a malformed URL, a host that is not found, an untrusted or expired certificate or a refused TLS handshake; once running, only a redirect or a malformed URL stops the process, and a host, certificate or TLS fault is waited out, with a warning that names `MARFA_API_URL` and the cause. A registration the server no longer holds is made again, and so is a type of the connector's deleted from the instance while it runs, where the key holds `types=write`; a connector running without fields its key may not add checks its key and types again before each scheduled run; a key that does not stops the process with exit code 1, naming the type, and a second loss within five minutes stops it with exit code 1 too. The heartbeat is sent every minute, apart from the hold's renewals, which are spaced by the instance's window. SIGTERM stops it cleanly. A connector that receives webhooks or carries changes back also looks between runs, every ten seconds unless `--every 15m --look-every 30s` says otherwise.

- **`node dist/main.js --setup <file>`**: once, by hand, for a connector with `setup`, which registers it with its vendor. It is handed `listen(page)`, which serves the page at an unguessable local address the log names, for the person to open in a browser, and waits for the vendor's redirect to its `callback`; a page that must name that address, such as a GitHub App manifest's `redirect_url`, is given as a function of it; the browser the vendor sends back is held at the callback, which answers once, until setup ends and it is told whether setup succeeded, or until the listen's `onward(address)`, called once the redirect has arrived, sends it on, such as to the page where the vendor asks for the next step; `endpoint()`, which makes the connector's own webhook endpoint and answers its address this once; and `secret`. The secrets it answers, each by the environment variable the connector declares for it, are written as JSON to `<file>`, which must not exist and must not sit in a folder that holds a `.git`, or under one, such as a checkout or a worktree; a file in the home directory is the usual choice, though setup cannot see a working tree whose git directory lives elsewhere, such as a dotfiles checkout of the home directory, so put it where nothing is tracked. The file is made, readable by its owner alone, before setup runs, so a secret a vendor hands over once is never lost to a file that cannot be written; it is removed if setup fails, and every endpoint that setup made is retired, or named with the command to retire it by hand where the instance would not. Move them into the secret store and delete the file. Each endpoint setup makes is labeled with the connector's label for it and when it was set up, which tells it apart in `marfa connectors endpoints list <connector-id>`, and setup names the id of each; once the vendor posts to the new one, retire any it replaces with `marfa connectors endpoints retire <connector-id> <endpoint-id>`, since a registration holds at most ten live endpoints. The kit never logs what setup answers; setup passes anything it logs itself through `secret` first. The environment needs only `MARFA_API_URL` and `MARFA_API_KEY`.

One process runs a connector at a time. Each run is made under a hold on the connector's registration, renewed a third of the instance's window apart, beside the heartbeat and let go when the process ends; a second process under the same key waits under `--every`, trying again a second after the hold would lapse, but no sooner than half a minute and no later than its next interval, so a process that took over from one stopped uncleanly runs within minutes, and one standing by beside a live process asks every few minutes; under `--once` it exits without running. Each says until when it is held. A run whose hold can no longer be trusted, because another process took it, it lapsed, or five sixths of the window the instance names (`ttl_ms`) passed since a renewal landed, stops before its next carry and keeps nothing more of what it read; the next run reads it again. The instance refuses a write to the connector's state or agreements from any process but the holder.

### launchd

`launchd.plist.example` runs the connector `--once` every fifteen minutes. Copy it to `~/Library/LaunchAgents/`, give it a label and the real paths, and load it with `launchctl bootstrap gui/$(id -u) <plist>`. Its `ProgramArguments` start the connector under a secrets tool, so the key and the vendor's token never sit in the plist. Run `--once`, a connector takes its deliveries only when it runs, so a webhook is acted on within the fifteen minutes; run it `--every` to act on one within seconds.

### A container

`Dockerfile` builds an image that runs one connector `--every 15m`. It copies only the workspace's manifests and the kit's and the connector's sources, so no other file in the checkout reaches the image. Build it from the repository root; its frozen install fetches the published client without a server checkout:

```bash
docker build -f template/Dockerfile --build-arg CONNECTOR=<name> -t <name> .
```

Pass the environment with `-e`. The container needs no volume: a new one picks up where the last left off, from the state kept on the instance.

A scope may opt into bounded inbound upsert retries with `forScope(name, { retry: { mode: "refetch" | "replay", context } })`, where `context` is a full SHA-256 of the caller's relevant nonsecret retry configuration. `scope.refusals.pending()` returns detached, acknowledged records with a derived `due` flag. Refetch mode requires the caller to retrieve each saved exact identity and reconstruct its complete current upsert. Replay mode stores a lossless JSON upsert intent; the caller dispatches due saved operations through ordinary scoped `upsert`. Prefer current complete input over an older replay for the same identity. Missing input, a conditional response, or inaccessible input preserves the record. The kit does not fetch or replay for the caller.

Only complete `invalid_properties` upserts and singleton `request_too_large` refusals after batch splitting qualify. Bounds are mode-specific: refetch stores the complete exact identity, fingerprint, context, refusal and due record; replay must also store the complete round-trip payload. A complete large singleton size refusal may qualify through a genuine point-refetch route even when its replay payload would not fit. File loaders and streams cannot be replayed. Unknown refusals, races, incomplete input, skipped bulk results, and undeclared or missing identities block scoped progress. Callers without a capability, and existing unscoped callers, gain no automatic advancement. A batch whose attempted writes all refuse with one code still fails.

A qualifying refusal and the position commit together in the existing state envelope. Records retain exact identity, intent fingerprint, effective context, and due time. Changed intent or context retries immediately; unchanged intent waits 24 hours after an acknowledged actual attempt. A record clears only after its row, connections, agreement, and state acknowledgment. Journal limits are 128 records and 64 KiB of serialized UTF-8 JSON, independently of the complete 512 KiB state envelope. Capacity blocks without eviction or identity truncation. Durable refusals remain visible in the complete run log beyond the generic condition-storage cap. Each checkpoint candidate must start from the latest acknowledged vendor state; the API replaces an explicit JSON value and does not merge speculative maps for the caller.

An unresolved record also prevents switching its scope to a different retry mode or removing its capability. Root state setters remain conservative while a journal is unresolved; independent explicitly capable scopes can still checkpoint from the latest acknowledged map.
